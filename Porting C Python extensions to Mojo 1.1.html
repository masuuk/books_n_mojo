Rewriting C Python extensions in Mojo

Yes, you can do it. Mojo builds shared libraries that Python imports like any compiled extension. Whether a given C module ports cleanly depends on how deeply it leans on the CPython C-API.

What works today

Mojo as extension module

Expose functions with PythonModuleBuilder, build with --emit shared-lib, import from Python.

Packaging

hatch-mojo can build Python extensions into wheels. Bundle the Mojo runtime libraries with bundle-libs = true.

Python from Mojo

Use Python.import_module() to keep calling existing Python packages while you port piece by piece.

Reuse C directly

If you only need the C library, a thin Mojo wrapper over its FFI is often cheaper than a full rewrite.

Mojo 1.0 stabilised the language core, but only a small initial set of standard library APIs carries the full stability guarantee. Expect some 1.x library churn and pin your version.

Fit by module type

Module typeDifficultyWhy
Numeric kernels, tight loopsEasyPure computation on ints, floats and buffers. This is Mojo's strongest ground.
Hashing, checksums, codecsEasyBytes in, bytes out, little Python object handling.
String and text parsersModerateStraightforward logic, but encoding and string conversion at the boundary need care.
Data-structure librariesModerateOwnership and lifetimes differ from C. Exposing the type to Python takes extra binding work.
Wrappers over system C librariesModeratePrefer calling the C library through Mojo FFI over reimplementing it.
Custom types with CPython slotsHardCode built around PyTypeObject slots, refcounts and GC hooks has no direct equivalent. You redesign it.
NumPy C-API or buffer protocol heavyHardDepends on array internals and conventions you must re-create or route through Python objects.
Callbacks, threads, GIL-sensitive codeHardCalling back into Python and managing the GIL from native code needs careful design and testing.

Porting steps

  1. Audit the C module. List every Py* call it makes and every type it exposes. That list sets your difficulty.
  2. Freeze behaviour. Write Python tests against the C version. It becomes your correctness oracle.
  3. Port one hotspot. Pick a pure function, rewrite it in Mojo, and keep the rest in C or Python.
  4. Bind it. Register it with PythonModuleBuilder and build the shared library.
  5. Run both against the tests. Compare outputs, then benchmark with realistic input sizes.
  6. Batch the boundary. Move loops into Mojo so you cross the Python boundary once, not per element.
  7. Package and pin. Build wheels with hatch-mojo and pin the Mojo version in your build requirements.

Minimal extension skeleton

Illustrative, based on the documented binding pattern. Check names and signatures against the Mojo 1.1 docs, since the binding API has been evolving.

# fastmod.mojo
from python import PythonObject
from python.bindings import PythonModuleBuilder
from os import abort

@export
fn PyInit_fastmod() -> PythonObject:
    try:
        var m = PythonModuleBuilder("fastmod")
        m.def_function[add]("add", docstring="Add two numbers")
        return m.finalize()
    except e:
        abort(String("could not create module: ", e))

fn add(a: PythonObject, b: PythonObject) raises -> PythonObject:
    return a + b
# build, then import from Python
mojo build fastmod.mojo --emit shared-lib -o fastmod.so
python -c "import fastmod; print(fastmod.add(2, 3))"

Pitfalls

Boundary overhead
Every Python-to-native call has a cost. A function called once per array element can be slower than the C version. Move the loop inside Mojo.
Documented limitations
The docs I found list no computed property getters and setters, a limited set of automatic type conversions, and manual builds for extensions that depend on non-stdlib Mojo packages. That page may predate 1.1, so recheck it.
Memory and ownership
C code often relies on manual lifetimes and aliasing. Mojo's ownership model is stricter, which catches bugs but forces redesigns of some data structures.
Runtime in wheels
Wheels with Mojo extensions need the Mojo runtime libraries bundled. Test installs in a clean environment without Mojo present.
Version drift
1.0 stabilised the language, not the whole standard library. Pin mojo==1.1.0 and retest on every upgrade.
