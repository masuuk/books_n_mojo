🤝 The Python Interop Bridge

Mojo's killer feature for data scientists: call any Python library directly from Mojo, use NumPy and pandas in Mojo code, and expose Mojo functions back to Python — all through one explicit interop module, where values crossing the boundary are copied.

Calling Python from Mojo

Mojo embeds a CPython interpreter. This means you can import and call any Python module directly from Mojo code, with automatic type conversion for common types. You do not need wrappers, bindings, or FFI declarations. Just import and call.

python_interop.mojo
// Mojo — call Python directly
from std.python import Python

// Import any Python module
var os = Python.import_module("os")
var sys = Python.import_module("sys")
print(os.getcwd())           // works!
print(sys.version)           // Python version string

// Call Python functions
var math = Python.import_module("math")
var root = math.sqrt(144.0)
print(root)                  // 12.0

// Use Python's json module
var json = Python.import_module("json")
var data = json.loads('{"name": "Mojo", "version": 1}')
print(data["name"])        // Mojo

// A Python exception surfaces as a Mojo error, so any
// function that calls into Python declares `raises`
def load_bad_json() raises:
    return json.loads("not json")

Mojo's Python interop is built-in — no wrappers, no external build configuration, no manual GIL management.

The GIL situation

Mojo runs Python code through the embedded CPython interpreter, which means the Global Interpreter Lock (GIL) still applies to Python calls. The benefit is that Mojo's own code runs outside the GIL at full native speed. The strategy: do your hot loops in Mojo, call Python for ecosystem access (file I/O, visualization, data loading).

Using NumPy, pandas, and scikit-learn from Mojo

The real power of Python interop is using the vast Python data science ecosystem from Mojo code. You can load data with pandas, manipulate it with NumPy, and train models with scikit-learn — all while writing Mojo for the performance-critical parts.

using Python data science libraries from Mojo
// Import the Python data science stack
from std.python import Python

var np = Python.import_module("numpy")
var pd = Python.import_module("pandas")
var plt = Python.import_module("matplotlib.pyplot")

// Load a CSV with pandas
var df = pd.read_csv("data/housing.csv")
print(df.head())
print(df.shape)

// Hand the frame to NumPy for computation
var features = df[["sqft", "beds", "baths"]].to_numpy()
var target = df["price"].to_numpy()

// Use scikit-learn for quick ML
var sklearn = Python.import_module("sklearn.linear_model")
var model = sklearn.LinearRegression()
model.fit(features, target)
print(model.score(features, target))

// Plot with matplotlib — pandas columns go straight in
plt.scatter(df["sqft"], df["price"])
plt.xlabel("Square Feet")
plt.ylabel("Price")
plt.savefig("scatter.png")
When to use Python vs native Mojo

Use Python interop for: data loading (pandas, CSV readers), visualization (matplotlib, seaborn), pre-built ML models (scikit-learn, HuggingFace), and anything where ecosystem breadth matters more than raw speed.

Use native Mojo for: custom training loops, tensor operations, SIMD-optimized kernels, real-time inference, and any code path that runs millions of times per second.

Calling Mojo from Python

The interop bridge works both ways. You can write performance-critical functions in Mojo and expose them to Python by building a shared library that Python loads with ctypes. This lets you keep your existing Python data pipeline while replacing the slow parts with Mojo.

fast_kernel.mojo
// Mojo — the fast function, written once
from std.math import sqrt

// A plain SIMD loop — this is the code worth moving
def fast_normalize(data: Span[Float32]) -> List[Float32]:
    var count = Float32(len(data))

    var total = 0.0
    for v in data:
        total += v
    var mean = total / count

    var variance = 0.0
    for v in data:
        var delta = v - mean
        variance += delta * delta
    var std = sqrt(variance / count)

    var result = List[Float32]()
    for v in data:
        result.append((v - mean) / std)
    return result

This is the incremental adoption story: keep your Python pipeline, replace slow functions one at a time with Mojo.

Getting the bridge in place

Mojo does not inject itself into Python's import system. The supported route is to build the Mojo code into a shared library and load it with ctypes: compile the def above with mojo build into a .so / .dll, then call it through a ctypes function pointer whose argument wraps the NumPy buffer. Keep the exported signature primitive — a pointer to a fixed-width float — because that is what both ABIs agree on; passing Mojo containers across the boundary is what makes this fragile.

Type mapping between Mojo and Python

When you cross the Python-Mojo boundary, types are automatically converted. Understanding the mapping helps you write efficient interop code and avoid surprises.

type conversion examples
// Mojo — type conversions at the boundary
from std.python import Python

var np = Python.import_module("numpy")

// Scalars convert implicitly in both directions
var scalar_array = np.array(1.0, dtype=np.float32)
var scalar: Float32 = scalar_array.item()

// Containers do not convert — build a Python list
var py_list = Python.list()
py_list.append(42)
py_list.append("hello")
print(py_list)  // [42, 'hello']

// Mojo List -> Python list, one element at a time
var mojo_values = List[Float64](1.5, 2.5, 3.5)
var out = Python.list()
for v in mojo_values:
    out.append(v)
var back = np.array(out)
print(back.shape)  // (3,)

// PythonObject for opaque handles
var pd = Python.import_module("pandas")
var df = pd.read_csv("data.csv")
var shape = df.shape  // Python tuple, access as PythonObject
print(shape[0], shape[1])
🚚 Sharing memory with NumPy

There is no implicit bridge between a NumPy array and a Mojo Span or Pointer. To avoid a copy you ask CPython for the buffer yourself — call PyObject_GetBuffer (or read the array's __array_interface__) through ctypes, then wrap the resulting address in a Pointer to the matching fixed-width dtype. That is worth doing for large ML datasets, where a deep copy of the feature matrix dominates the runtime.

As of Mojo 1.x final

Interop got a significant upgrade: PythonObject arithmetic, comparison, and membership operators now dispatch through CPython's abstract protocols (PyNumber_Add, PyObject_RichCompare, ...) instead of a Python-level attribute lookup plus bound-method call — roughly 12x faster on the interop hot path, with standard Python semantics including reflected operands (__radd__ et al). The boundary itself is unchanged, though: scalars cross implicitly, containers still have to be built by hand, and buffers still have to be shared deliberately.
