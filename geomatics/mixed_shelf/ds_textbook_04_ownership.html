🔐 Ownership & Borrowing

Mojo's memory safety model — how ownership, borrowing, and exclusivity rules eliminate data races and use-after-free bugs without a garbage collector, while staying simpler than a full borrow checker.

Why ownership matters

Every language must answer the question: who is responsible for freeing this memory? Python uses a garbage collector (reference counting + cycle detector). C lets you manage it manually (and crash). Some systems languages use a compile-time ownership system. Mojo follows that approach but with a key design goal: make the common case easy and the hard case possible.

The problem ownership solves is real and costly. In Python, two variables can point to the same list, and modifications through one affect the other silently. In C, you can free memory and then accidentally use it. In Mojo, the compiler tracks every value's lifetime and rejects code that could cause memory errors.

ownership.mojo
# Mojo — values have a single owner
var a = [1, 2, 3]   # a owns the list
var b = a              # COMPILE ERROR — can't copy implicitly
var c = a^             # OK — moves ownership from a to c
# a is now invalid — can't use it
print(c)                # [1, 2, 3]

# Explicit copy when you need both
var d = [4, 5, 6]
var e = d.copy()       # deep copy — both d and e own their data
d.append(7)            # only affects d
print(e)                # [4, 5, 6] — unchanged

Mojo enforces single ownership at compile time. Python's reference semantics are simpler but sacrifice control: the two names for one list above cost you nothing, but the d = d.copy() / copy.deepcopy(a) calls that buy Mojo's behaviour back are explicit in Python, and freeing is the collector's problem — which is also where the hidden copies, the race conditions and the unpredictable pauses come from.

The data science angle

In ML pipelines, you often transform large tensors through multiple stages. Ownership semantics ensure that intermediate tensors are freed as soon as they're no longer needed — no garbage collector pausing your training loop mid-batch. This is why Mojo can maintain Python-like syntax while delivering C-like performance.

Argument conventions: how values flow into functions

Mojo uses five argument conventions to make ownership explicit at function boundaries. This is where Mojo diverges most from Python, which passes everything by reference.

ConventionKeywordWhat happensUse case
Default(none)Read-only borrow — no copy, no moveMost function arguments
MutablemutMutable borrow — can modify in placeIn-place transformations
OwnedvarTakes ownership — caller can't use after callConsuming / transforming data
ReferencerefMutable reference — must be an lvalueStruct methods that modify self
OutoutInitializes the parameter — caller gets the valueConstructors, factory functions
arg_conventions.mojo
# Default — read-only borrow
def length(s: String) -> Int:
    return len(s)  # can read, can't modify

# mut — mutable borrow (in-place modification)
def append_exclamation(mut s: String):
    s += "!"  # modifies the original

var greeting = "Hello"
append_exclamation(greeting)
print(greeting)  # "Hello!"

# var — takes ownership (consumes the value)
def process(var data: List[Int]) -> Int:
    var total = 0
    for item in data:
        total += item
    return total

var numbers = [1, 2, 3]
var result = process(numbers^)  # moves numbers into process
# numbers is now invalid

# out — output parameter (constructs the value)
def create_vector(out result: List[Int], size: Int):
    result = List[Int]()  # initializes result
    for i in range(size):
        result.append(i * i)

var squares: List[Int]
create_vector(squares, 5)
print(squares)  # [0, 1, 4, 9, 16]

Mojo's argument conventions make the same borrow/move distinctions that systems languages make — but with more readable syntax.

Why this matters for ML code

When you pass a 10 GB tensor to a function, you absolutely do not want to copy it. The default (borrow) convention means the function reads the tensor without copying. If the function needs to modify it in place (e.g., normalization), you use mut. If the function consumes and transforms it (e.g., adding a layer), you use var. The compiler guarantees you never accidentally copy a massive tensor.

Transfer with ^ — explicit ownership handoff

The ^ operator is Mojo's explicit ownership transfer. When you write b = a^, you're telling the compiler: "move the value from a into b. After this line, a is dead." This is the only way to transfer ownership of a non-Copyable value.

transfer patterns in practice
# Pattern 1: Transfer into a function
var model_data = load_training_data()
var stats = compute_statistics(model_data^)  # model_data is moved
# Can't use model_data anymore — it's been consumed

# Pattern 2: Move into a collection
var results = List[Experiment]()
for config in configs:
    results.append(run_experiment(config^))

# Pattern 3: Swap ownership
var old_buffer = allocate_buffer()
var new_buffer = old_buffer^  # old_buffer is now empty

# Pattern 4: Return to transfer out
def transform(var data: List[Int]) -> List[Int]:
    for i in range(len(data)):
        data[i] *= 2
    return data^  # transfers ownership back to caller

var raw = [1, 2, 3]
var doubled = transform(raw^)
print(doubled)  # [2, 4, 6]

Mojo also provides an inference shortcut: if a function takes a var parameter and the original variable is never used again, the compiler automatically inserts the ^ for you. This is called last-use transfer:

last-use inference
var data = [1, 2, 3]

# Both of these are equivalent:
process(data^)  # explicit transfer
process(data)   # implicit — compiler sees data isn't used after

# But this would NOT auto-transfer:
process(data)
print(data)      # data is used again — no auto-transfer

Exclusivity rules: no data races, ever

Mojo enforces three fundamental rules at compile time:

  • Rule 1: You can have either one mutable reference or any number of immutable references to a value — never both.
  • Rule 2: References must always be valid — no dangling pointers, no use-after-free.
  • Rule 3: A value's owner decides when it's destroyed — deterministic destruction, no GC.
exclusivity.mojo
# Multiple immutable borrows — ALLOWED
var tensor = create_tensor()
var a = tensor.shape   # immutable borrow
var b = tensor.shape   # another immutable borrow
print(a, b)              # both valid simultaneously

# Mutable borrow — EXCLUSIVE
def normalize(mut t: Tensor[DType.float32]):
    t /= t.max()

normalize(tensor)  # mutable — no other borrows allowed

# This would be a COMPILE ERROR:
var data = [1, 2, 3]
var slice = data[...]   # immutable borrow of data
data.append(4)          # ERROR — can't mutate while borrowed
print(slice)

# Deterministic destruction
def process_batch():
    var buffer = allocate(1024)
    # ... use buffer ...
    return  # buffer.__del__ called HERE, deterministically
# No GC pause, no finalize, no waiting

Mojo prevents data races at compile time — the same guarantee systems programmers rely on, without the extra syntax.

Ownership at a glance

Mojo's ownership model makes deliberate choices to keep the common case simple:

FeatureMojoPython
Default argumentImmutable borrow (no syntax)Pass-by-reference
Mutable borrowmut keywordAll objects shared by reference
Ownership transfer^ sigilNot a concept — GC manages memory
Lifetime trackingNone needed (inferred)Handled by the garbage collector
Implicit copiesNever (must use .copy())Always shared; copies only when you ask
The big win for data scientists

Python programmers never think about ownership — and that's by design. But it means Python can't guarantee memory safety without a GC. Mojo gives you the option to opt into precise memory control when you need it (ML training loops, real-time inference) while keeping the simple Python-like syntax for everything else. The level of strictness is your signal: an unannotated def is the friendly path, a fully-annotated def is the fast path.
