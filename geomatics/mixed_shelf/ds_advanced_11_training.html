🏋️ Training Loops

Distributed data-parallel, mixed precision, checkpointing, and learning rate scheduling in Mojo.

Distributed Data-Parallel Training

When a single GPU can't hold your dataset or model, you distribute the workload. Mojo's distribute module provides first-class support for data-parallel training with minimal boilerplate. Each rank holds a full copy of the model and processes a shard of the data, syncing gradients via all-reduce.

Unlike PyTorch's DistributedDataParallel, which requires a launcher script and environment variables, Mojo manages rank assignment and communication topology directly in the compiler.

Mojo 1.x
from distributed import DistConfig, all_reduce
from tensor import Tensor, Float32

def train_epoch(model: Model, loader: DataLoader, cfg: DistConfig):
    for batch in loader.shard(cfg.rank, cfg.world_size):
        var loss = model.forward(batch.data, batch.labels)
        loss.backward()
        // Synchronize gradients across all ranks
        for param in model.parameters():
            all_reduce(param.grad, op=ReduceOp.AVG, group=cfg.group)
        model.optimizer.step()
        model.zero_grad()
Key Difference

In Mojo, gradient synchronization is explicit — you call all_reduce yourself. This gives you fine-grained control over when and how communication happens, which is critical for overlapping computation with communication.

Topology Configuration

Mojo supports ring, tree, and hierarchical all-reduce topologies. For multi-node training, you can specify the number of nodes and GPUs per node:

Mojo 1.x
var cfg = DistConfig(
    world_size=8,
    rank=0,
    backend=Backend.NCCL,
    topology=Topology.RING
)

// For multi-node: set node rank and IP
cfg.set_node(
    node_rank=0,
    node_count=2,
    master_addr="10.0.0.1",
    master_port=29500
)

Mixed Precision Training

Mixed precision reduces memory usage and increases throughput by performing forward and backward passes in FP16 or BF16 while maintaining a FP32 master copy of the weights. Mojo's type system makes this composable — you can annotate computation blocks with precision levels.

Mojo 1.x
from precision import amp, autocast
from tensor import Tensor, Float16, Float32

def train_step(model: Model, batch: Batch):
    // Autocast wraps forward pass in reduced precision
    with autocast(dtype=Float16):
        var logits = model.forward(batch.data)
        var loss = cross_entropy(logits, batch.labels)

    // Loss scaling prevents underflow in FP16 gradients
    var scaled_loss = loss * amp.scale_factor()
    scaled_loss.backward()

    // Unscaled gradients in FP32 master weights
    amp.unscale(model.optimizer)
    model.optimizer.step()
    amp.update_scale()
Tip: BF16 vs FP16

BF16 has the same exponent range as FP32, so it's less prone to overflow/underflow. Use BF16 when possible — it's the default for most modern accelerators including NVIDIA Ampere+ and Google TPUs.

Automatic Loss Scaling

Mojo's amp module implements dynamic loss scaling that adjusts the scale factor based on gradient statistics. Unlike PyTorch's static or manual scaling, this runs as a compiler intrinsic with zero runtime overhead.

Checkpointing

Long training runs must be resilient to failure. Mojo's checkpointing system saves model state, optimizer state, and training metadata atomically — either the entire checkpoint is written or nothing is, preventing corruption from interrupted writes.

Mojo 1.x
from checkpoint import CheckpointManager, CheckpointConfig
from time import now

var ckpt_cfg = CheckpointConfig(
    dir="/checkpoints/run_001",
    max_keep=3,
    format=Format.SAFETENSORS,
    async_write=True
)

var mgr = CheckpointManager(ckpt_cfg)

for epoch in range(max_epochs):
    train_epoch(model, loader, cfg)
    if epoch % 5 == 0:
        // Atomic save: metadata.json written last
        mgr.save({
            "model": model.state_dict(),
            "optimizer": optimizer.state_dict(),
            "epoch": epoch,
            "timestamp": now()
        })
Atomic Writes

Mojo writes checkpoint data to a temporary file first, then renames it into place. This means a crash mid-write won't corrupt your last good checkpoint. PyTorch's torch.save writes directly to the target file, risking partial writes.

Incremental Checkpointing

For large models, saving full state every N steps is expensive. Mojo supports incremental checkpoints that only write tensors that changed since the last save:

Mojo 1.x
var mgr = CheckpointManager(ckpt_cfg)

// First save: full checkpoint
mgr.save(model.state_dict(), full=True)

// Subsequent saves: only diff from previous
for step in range(1000):
    train_step(model, batch)
    if step % 100 == 0:
        mgr.save(model.state_dict(), full=False)
        // Only ~2-5% of tensors typically change per step

Learning Rate Scheduling

The learning rate schedule is one of the most impactful hyperparameters in training. Mojo provides composable schedulers that can be combined and checkpointed alongside your model.

Mojo 1.x
from optim.lr_scheduler import (
    CosineAnnealingLR, WarmupLinear, SequentialScheduler
)

// Build a warmup + cosine decay schedule
var schedule = SequentialScheduler([
    WarmupLinear(
        warmup_steps=1000,
        start_lr=1e-6,
        peak_lr=3e-4
    ),
    CosineAnnealingLR(
        total_steps=50000,
        min_lr=1e-6
    )
])

// Composable: combine with gradient accumulation
var effective_lr = schedule.lr_at(step) * cfg.grad_accum_steps

// Stateful: save/restore with checkpoint
mgr.save({
    "model": model.state_dict(),
    "scheduler": schedule.state_dict()
})
Tip: Learning Rate Finder

Mojo includes a built-in LR range test that trains for N steps with exponentially increasing learning rates. It outputs a loss-vs-LR plot to help you find the optimal range before committing to a full training run.

Custom Schedules

You can write custom schedules by implementing the LRSchedule protocol:

Mojo 1.x
struct OneCycleLR:
    var max_lr: Float32
    var total_steps: Int
    var pct_warmup: Float32

    def lr_at(self, step: Int) -> Float32:
        var pct = Float32(step) / Float32(self.total_steps)
        if pct < self.pct_warmup:
            return self.max_lr * (pct / self.pct_warmup)
        else:
            var decay_pct = (pct - self.pct_warmup) / (1.0 - self.pct_warmup)
            return self.max_lr * (0.5 * (1.0 + cos(pi * decay_pct)))
