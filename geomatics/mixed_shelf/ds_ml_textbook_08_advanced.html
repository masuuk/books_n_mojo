GPU Acceleration

Mojos ultimate performance promise is GPU-native computation. Unlike Python, where GPU access requires CUDA bindings or framework-specific APIs, Mojo treats the GPU as just another device you can target with the same language syntax.

Mojo compiles kernels to PTX (NVIDIA) or Metal Shading Language (Apple) using MLIR as the intermediate representation. This means the same Mojo source code can target different GPU architectures.

from std.gpu import thread_idx, block_idx, block_dim
from max.gpu.host import DeviceContext
from std.math import ceildiv

def add_kernel(A: DeviceBuffer, B: DeviceBuffer,
                C: DeviceBuffer, n: Int32):
    var idx = block_idx.x * block_dim.x + thread_idx.x
    if idx < n:
        C[idx] = A[idx] + B[idx]

def gpu_add() raises:
    comptime N = 1024
    comptime BLOCK = 256

    var ctx = DeviceContext()
    var A_gpu = ctx.enqueue_create_buffer[DType.float32](N)
    var B_gpu = ctx.enqueue_create_buffer[DType.float32](N)
    var C_gpu = ctx.enqueue_create_buffer[DType.float32](N)
    # ... copy inputs with ctx.enqueue_copy(...) ...

    # Launch kernel on the GPU
    ctx.enqueue_function[add_kernel](
        A_gpu, B_gpu, C_gpu, Int32(N),
        grid_dim=ceildiv(N, BLOCK), block_dim=BLOCK,
    )
    ctx.synchronize()
💡 Key Insight:

Mojos GPU story is different from PyTorch: the kernel is written in the same language as your host code, sharing types and data structures. No language boundary between CPU and GPU code.

PyTorch draws that boundary twice. An element-wise add is easy — A = torch.randn(N, device="cuda") and C = A + B, because the framework dispatches the whole tensor expression to a kernel it already ships. A custom kernel is where the boundary bites: torch.utils.cpp_extension.load compiles kernel.cu at runtime and hands you back an opaque callable, so the kernel is C++/CUDA, it cannot see your model's types, and its buffers are raw pointers with no shape or dtype attached. The Mojo pane above has neither problem — add_kernel takes the same DeviceBuffer type the host code holds, and the launch is one ctx.enqueue_function[add_kernel](...) with grid_dim and block_dim as arguments rather than a build step.

Deployment and Production

Mojo compiles to a standalone binary, making deployment straightforward. Unlike Python deployments that need a runtime, dependency management, and virtual environments, a Mojo binary includes everything it needs.

Deployment Options

  • Standalone binary: Compile with mojo build -o model_server model.mojo and deploy a single executable.
  • Shared library: Build with mojo build --lib to create a .so/.dylib that other languages can call via FFI.
  • Docker container: Use the Mojo base image for containerized deployment with minimal image size.
  • Edge deployment: Cross-compile for ARM to deploy on edge devices like Jetson or mobile.
from inference import serve, Request, Response

struct ModelServer:
    var model: TwoLayerNet

    def __init__(out self, path: String):
        self.model = load_model(path)

    def handle(self, req: Request) -> Response:
        var input = parse_input(req.body)
        var prediction = self.model.forward(input)
        return Response(
            status=200,
            body=to_json(prediction),
        )

def main():
    var server = ModelServer("model.bin")
    serve(server.handle, port=8080)
    print("Server running on port 8080")
🚀 Pro Tip:

Mojos binary deployment means no Python version conflicts, no pip install failures, and no __pycache__ directories. The compiled binary is self-contained and deterministic.

The shape of the serving code is the other half of the story. The FastAPI version is a framework you install, decorate, and hand to an ASGI server: @app.post("/predict"), a torch.no_grad() block, pred.tolist() to make the result JSON-shaped, and uvicorn.run(app, host="0.0.0.0", port=8080) to keep it alive. The Mojo struct ModelServer replaces all of that with a handle method that takes a Request and returns a Response, plus one serve(server.handle, port=8080) call. The prediction never leaves a tensor on its way out, and the thing you ship is the executable from mojo build -o model_server model.mojo — not a virtualenv.

PyTorch and ONNX Interop

You don't have to rewrite everything from scratch. Mojo can interoperate with existing ML ecosystems through ONNX, PyTorch export, and Python interop layers. This lets you migrate incrementally.

Loading PyTorch Models

The most common migration path is: train in PyTorch, export to ONNX, load in Mojo for inference. Mojo's ONNX runtime can execute pre-trained models with full performance.

Export is a one-time, offline step and it happens on the PyTorch side — it is the half of the workflow that is not Mojo, and the pane below is the half that is. The export call is torch.onnx.export(model, dummy, "resnet50.onnx", ...), where dummy is a correctly shaped torch.randn(1, 3, 224, 224) input and dynamic_axes={"input": {0: "batch"}} is what keeps the batch dimension free afterwards; name the input and output tensors with input_names and output_names so the graph is readable at load time. Once the file exists, everything from that point on is the Mojo pane.

💡 Coming from Python:

When the dependency is a library you cannot export — a preprocessor, a tokenizer, a metric that only exists as a Python package — reach for the interop layer instead of porting it. from std.python import Python followed by var np = Python.import_module("numpy") hands you a live handle on the installed module, and the call goes through to the real implementation. The result is a Mojo program that is genuinely mixed: your own code compiled, one library borrowed. Use ONNX for anything that exports cleanly — it is the faster path, because the graph runs natively — and interop for the leftovers.

from onnx import ONNXModel

# Load a pre-trained ONNX model
var model = ONNXModel.load("resnet50.onnx")

# Run inference
var input_tensor = preprocess_image("photo.jpg")
var output = model.run(input_tensor)

# Get top-5 predictions
var predictions = softmax(output)
for i in range(5):
    var idx = argmax(predictions)
    print("Class", idx, ":", predictions[idx])
    predictions[idx] = 0.0
💡 Key Insight:

ONNX is the universal interchange format for ML models. By supporting ONNX, Mojo gains access to the entire ecosystem of pre-trained models — from Hugging Face, torchvision, and custom PyTorch exports.

Production ML Pipelines

In production, a model is just one piece of the puzzle. You need data preprocessing, feature engineering, batching, caching, monitoring, and A/B testing. Mojo's type system and performance make it ideal for building entire pipelines in one language.

from pipeline import Pipeline, stage
from io import FileSource, BatchedSource

struct InferencePipeline:
    var model: TwoLayerNet
    var preprocessor: StandardScaler

    def __init__(out self, model_path: String):
        self.model = load_model(model_path)
        self.preprocessor = load_scaler(model_path)

    def run(self, source: FileSource) -> Tensor[Float32]:
        var pipe = Pipeline()
        pipe.add(stage("read", source.read_csv))
        pipe.add(stage("preprocess",
                       self.preprocessor.transform))
        pipe.add(stage("batch",
                       BatchedSource[64].batch))
        pipe.add(stage("predict",
                       self.model.forward_batch))
        return pipe.execute()

# Run end-to-end pipeline
var pipeline = InferencePipeline("model.bin")
var results = pipeline.run(FileSource("data.csv"))
⚠️ Watch Out:

Mojo's pipeline APIs are newer than the rest of the standard library. In practice, you might still need to build your own pipeline abstractions using Mojo's struct system. The key advantage is that every stage runs at compiled speed — no Python interpreter overhead between stages.

Compare what the stage list costs in the pandas version: pd.read_csv builds a DataFrame, StandardScaler().fit_transform(df.values) converts it back out to an array, torch.tensor(X).float() copies it a third time, and torch.split(..., 64) hands back a tuple of views that a list comprehension walks before torch.cat reassembles the result. Four full traversals of the data and at least three copies, all of them ordinary data-movement work. The Mojo pane names the same four stages — read, preprocess, batch, predict — and hands each one a function, so there is nothing to copy between them and nothing to concatenate afterwards.

The Future of Mojo

Mojo hit 1.0 (with source stability) and its entire compiler, toolchain, and standard library are now open source under Apache 2.0 — so the roadmap is more visible than ever. Developments that will expand its place in the ML ecosystem include:

  • Open compiler contributions: The standard library already accepts community contributions; compiler and tooling contributions are planned to open up as well.
  • Full Python interop: Seamless calling of any Python library from Mojo, enabling gradual migration of existing codebases.
  • Distributed computing: First-class support for multi-node training and inference, built on MLIRs distributed dialect.
  • Auto-tuning: The compiler will automatically select optimal SIMD widths, tile sizes, and parallelization strategies based on the target hardware.
  • WebAssembly target: Compile Mojo to WASM for browser-based ML inference with near-native performance.
  • Ecosystem growth: As the language matures, expect libraries for computer vision, NLP, and reinforcement learning written natively in Mojo.
💡 Key Insight:

Mojos goal is not to replace Python — it's to eliminate the need for two languages. Write your entire ML stack in Mojo: data loading, preprocessing, model definition, training, optimization, deployment. One language, one toolchain, one binary.
