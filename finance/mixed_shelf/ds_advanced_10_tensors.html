🧬 Tensor Architecture

Shape inference, memory layouts, compute kernels, and the design of high-performance tensor systems in Mojo.

Shape Inference

Tensor operations require compatible shapes. Shape inference determines output shapes from input shapes without executing the computation. This catches shape errors at compile time and enables optimizations like memory pre-allocation.

Broadcasting Rules

Broadcasting allows operations on tensors with different shapes by implicitly expanding dimensions. The rules are: (1) dimensions are aligned from the right, (2) dimensions of size 1 are broadcast to match, (3) missing dimensions are treated as size 1.

Mojo 1.x
from tensor import Tensor, TensorSpec, TensorShape

def broadcast_shapes(a: TensorShape, b: TensorShape) raises -> TensorShape:
    // Align dimensions from the right
    var ndim = max(a.rank(), b.rank())
    var result = List[Int]()

    for i in range(ndim):
        var dim_a = 1 if i < a.rank() else a[i]
        var dim_b = 1 if i < b.rank() else b[i]

        if dim_a != dim_b and dim_a != 1 and dim_b != 1:
            raise "Cannot broadcast shapes"

        result.append(max(dim_a, dim_b))

    return TensorShape(result)


// Example: (3, 1) + (1, 4) -> (3, 4)
var a = Tensor[Float32](TensorShape(3, 1))
var b = Tensor[Float32](TensorShape(1, 4))
var c = a + b  // shape: (3, 4) -- broadcast automatically


// Reshape with compile-time dimensions
def flatten_batch[N: Int, C: Int, H: Int, W: Int](
    t: Tensor[Float32]
) -> Tensor[Float32]:
    return t.reshape(N, C * H * W)
Compile-time shape checking:

Mojo's parametric types let you encode tensor shapes as type parameters. Shape mismatches are caught at compile time, not runtime. A Tensor[Float32, 3, 224, 224] is a different type from Tensor[Float32, 3, 128, 128].

Tensor Layouts

A tensor's layout defines how logical indices map to physical memory addresses. The choice of layout affects cache performance, vectorization, and interoperability with other frameworks.

Common Layouts

  • Row-major (C-contiguous): Last dimension varies fastest. Default in NumPy, PyTorch.
  • Column-major (Fortran-contiguous): First dimension varies fastest. Used in MATLAB, Julia.
  • Strided: Arbitrary strides between dimensions. Supports views and broadcasting without copying.
  • Packed: No padding, tightly packed. Best for compute, but limits some operations.
Mojo 1.x
from tensor import Tensor, LayoutTensor, NDBuffer

// Mojo encodes stride pattern at compile time
def row_major_index(i: Int, j: Int, cols: Int) -> Int:
    return i * cols + j

def col_major_index(i: Int, j: Int, rows: Int) -> Int:
    return j * rows + i


// Strided tensor view -- no data copy
def transpose_view(
    t: Tensor[Float32]
) -> Tensor[Float32]:
    // Swaps strides, not data
    var new_strides = (t.stride(1), t.stride(0))
    return Tensor[Float32](
        data=t.data(),
        shape=TensorShape(t.shape[1], t.shape[0]),
        strides=new_strides
    )


// Compute optimal stride for alignment
def aligned_stride(
    shape: TensorShape,
    elem_size: Int,
    alignment: Int = 64
) -> Int:
    var stride = shape[1] * elem_size
    return (stride + alignment - 1) & ~(alignment - 1)

Compute Kernels

A kernel is a tightly optimized function that operates on a small tile of data. Modern tensor frameworks decompose large operations into kernel calls. Mojo's SIMD primitives make writing high-performance kernels straightforward.

Mojo 1.x
from sys.intrinsics import (
    simd_load, simd_store, simd_add, simd_mul
)

// SIMD vectorized element-wise add kernel
def simd_add_kernel(
    a: Pointer[Float32],
    b: Pointer[Float32],
    result: Pointer[Float32],
    n: Int
):
    var i = 0
    var simd_width = 8

    // Vectorized loop
    while i + simd_width <= n:
        var va = simd_load[DType.float32, 8](a + i)
        var vb = simd_load[DType.float32, 8](b + i)
        simd_store(result + i, simd_add(va, vb))
        i += simd_width

    // Scalar tail
    while i < n:
        result[i] = a[i] + b[i]
        i += 1


// ReLU kernel with SIMD
def simd_relu_kernel(
    input: Pointer[Float32],
    output: Pointer[Float32],
    n: Int
):
    var zero = SIMD[DType.float32, 8](0.0)
    var i = 0

    while i + 8 <= n:
        var v = simd_load[DType.float32, 8](input + i)
        simd_store(output + i, v.max(zero))
        i += 8

    while i < n:
        output[i] = max(input[i], 0.0)
        i += 1
Mojo kernel advantage:

In Python, you need Numba JIT or Cython to write SIMD kernels. In Mojo, SIMD intrinsics are first-class citizens -- the compiler auto-vectorizes scalar loops and gives you explicit control over vector width when needed.

Tensor Memory Layout

Understanding how tensors occupy memory is essential for performance. The memory layout determines cache line utilization, prefetching effectiveness, and whether operations are memory-bound or compute-bound.

Cache-Friendly Access Patterns

Modern CPUs load data in cache lines (typically 64 bytes = 16 Float32 values). Sequential access along the contiguous dimension achieves peak memory bandwidth. Strided access causes cache misses and can be 10-100x slower.

Mojo 1.x
from tensor import Tensor

// Memory layout analysis
def analyze_layout(t: Tensor[Float32]):
    print("Shape:", t.shape)
    print("Strides:", t.strides())
    print("Element size:", t.element_size(), "bytes")
    print("Total bytes:", t.nbytes())

    // Check if contiguous
    var is_contiguous = True
    for i in range(t.rank() - 1):
        if t.stride(i) != t.shape[i + 1] * t.stride(i + 1):
            is_contiguous = False
            break
    print("Contiguous:", is_contiguous)


// Pre-allocate output for fused operations
def fused_matmul_add(
    A: Tensor[Float32],
    B: Tensor[Float32],
    bias: Tensor[Float32],
    output: Tensor[Float32]  // pre-allocated
):
    // C = A @ B + bias (fused, no temp allocation)
    matmul(A, B, output)
    for i in range(output.shape[0]):
        for j in range(output.shape[1]):
            output[i, j] += bias[j]

💡 Key takeaway:

Always prefer operations along the contiguous (innermost) dimension. If you need to operate along a non-contiguous axis, consider transposing the tensor first (zero-cost view) or materializing a contiguous copy for the hot loop.
