MojoTest

ML testing is fundamentally different from traditional software testing. A function can be numerically correct but still useless if it converges poorly, overflows in production, or uses too much memory. MojoTest is a testing framework designed for ML workloads -- it combines correctness checks, numerical stability tests, and performance regression detection.

Mojo 1.x
from testing import TestCase, assert_close, assert_no_nan

class AttentionTest(TestCase):
    def test_output_shape(self):
        var attn = MultiHeadAttention(n_heads=8, d_model=512)
        var x = Tensor[Float32](1, 10, 512)
        var out = attn(x)
        assert_close(out.shape, TensorShape(1, 10, 512))

    def test_no_nan(self):
        var x = Tensor[Float32](random_floats(shape=(4, 128, 768)))
        var out = model.forward(x)
        assert_no_nan(out)

    def test_numerical_stability(self):
        // Test with extreme values
        var x = Tensor[Float32](1e6, shape=(1, 1, 512))
        var out = model.forward(x)
        assert_no_nan(out)
        // Output should be finite even with large inputs
        assert all(out.to_list().map(is_finite))
Built-in Assertions

MojoTest provides ML-specific assertions: assert_close (with tolerance), assert_no_nan, assert_no_inf, assert_converges (checks loss decreases), and assert_within_memory (fails if peak memory exceeds a limit).

Performance Regression Tests

MojoTest can detect performance regressions by comparing against baseline measurements:

Mojo 1.x
from testing import PerformanceTest, baseline

class AttentionPerfTest(PerformanceTest):
    def test_throughput(self):
        var attn = MultiHeadAttention(n_heads=8, d_model=512)
        var x = Tensor[Float32](32, 128, 512)

        // Baseline from last commit (auto-loaded)
        var prev = baseline("attention_throughput")

        // Measure current performance
        var current = self.benchmark(
            def(): attn.forward(x),
            iterations=1000
        )

        // Fail if greater than 5% regression
        self.assert_within_pct(current, prev, tolerance=5.0)

Artifact Caching

ML pipelines are expensive. Mojo's artifact cache stores compiled models, preprocessed datasets, and intermediate results, keyed by their inputs' content hashes. If nothing changed, the cache is reused -- saving hours of compute.

Mojo 1.x
from ci import ArtifactCache, CacheKey

var cache = ArtifactCache(
    backend=CacheBackend.S3,
    prefix="ml-pipeline",
    ttl_days=30
)

// Hash-based caching: skip if inputs unchanged
var key = CacheKey.from_files([
    "data/raw.parquet",
    "src/preprocess.mojo",
    "config/hyperparams.yaml"
])

if cache.exists(key):
    var dataset = cache.load(key)
    print("Cache hit -- skipping preprocessing")
else:
    var dataset = preprocess(raw_data)
    cache.save(key, dataset)
    print("Cache miss -- preprocessing and storing")

// Model compilation cache
var model_key = CacheKey.from_config({
    "model": "transformer_v3",
    "precision": "fp16",
    "target": "cuda",
    "weights_hash": weights.sha256()
})

var compiled = cache.get_or_compile(model_key, def():
    compile_model(model, CompileConfig(precision=Float16))
)
Tip: Cache Invalidation

Content hashing means cache invalidation is automatic -- change the code or data, and a new artifact is created. No manual version tags or timestamps needed. The old cache entry is kept until its TTL expires.

Testing Strategies

ML systems need a layered testing strategy. Each layer catches different failure modes, and together they provide confidence that your pipeline works correctly in production.

The ML Testing Pyramid

  • Unit tests -- individual operations (attention, layer norm, loss functions)
  • Integration tests -- forward/backward pass through the full model
  • Data tests -- schema validation, distribution checks, missing values
  • Performance tests -- throughput, latency, memory usage
  • Model quality tests -- accuracy on held-out sets, fairness metrics
  • Canary tests -- shadow traffic on a small production slice
Mojo 1.x
from testing import TestCase, DataTest
from data import Dataset

class DataValidationTest(DataTest):
    def test_schema(self):
        var ds = Dataset.load("train.parquet")
        self.assert_columns(ds, ["text", "label", "timestamp"])
        self.assert_dtype(ds["label"], Int64)
        self.assert_range(ds["label"], min=0, max=9)

    def test_distribution(self):
        var ds = Dataset.load("train.parquet")
        // Ensure no class has less than 5% representation
        var dist = ds.column("label").value_counts(normalized=True)
        for label, pct in dist:
            self.assert_gt(pct, 0.05,
                msg=f"Class {label} underrepresented at {pct:.1%}")

    def test_no_leakage(self):
        // Ensure train/val/test splits don't overlap
        var train = Dataset.load("train.parquet")
        var val = Dataset.load("val.parquet")
        self.assert_no_overlap(train.ids, val.ids)
Data Tests Are Critical

The most common production ML failures aren't model bugs -- they're data issues. Schema drift, missing values, distribution shifts, and train-serve skew cause more outages than code errors. Mojo's DataTest class makes data validation a first-class testing concern.

Deployment Pipelines

A complete ML CI/CD pipeline in Mojo connects data validation, training, evaluation, and deployment. Here's a production-ready pipeline defined in code:

Mojo 1.x
GitHub Actions (YAML)
from ci import Pipeline, Stage, Gate, Trigger

var pipeline = Pipeline(
    name="llm-training",
    trigger=Trigger.push(branch="main"),

    stages=[
        Stage("validate_data",
            command="mojo test tests/data/",
            cache=CacheKey.from_files(["data/**"])
        ),
        Stage("train",
            command="mojo train.py --config config/prod.yaml",
            gpu=8,
            timeout="4h",
            depends_on=["validate_data"]
        ),
        Stage("evaluate",
            command="mojo eval.py --model artifacts/model.mojomodel",
            gates=[
                Gate.min_accuracy(0.92),
                Gate.max_latency_ms(50),
                Gate.max_memory_gb(4.0),
            ]
        ),
        Stage("deploy_canary",
            command="mojo-serve deploy --traffic 5%",
            auto_rollback=True,
            monitor_minutes=30
        ),
        Stage("deploy_full",
            command="mojo-serve deploy --traffic 100%",
            requires_approval=True
        ),
    ]
)
# .github/workflows/train.yml
name: ML Pipeline
on:
  push:
    branches: [main]

jobs:
  train:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: mojo test tests/data/
      - run: mojo train.py --config config/prod.yaml
        env:
          GPU_COUNT: 8
      - run: mojo eval.py --model artifacts/model.mojomodel
      - run: mojo-serve deploy --traffic 5%
Tip: Canary Deployments

Always deploy ML models to a small percentage of traffic first. MojoServe's canary mode monitors error rates, latency, and prediction distributions in real-time. If any metric deviates, it automatically rolls back within seconds.

Pipeline Best Practices

  • Version everything -- code, data, config, and model artifacts should all be versioned
  • Gate on metrics -- don't deploy if accuracy drops below threshold
  • Cache aggressively -- preprocessing and compilation caches save hours of CI time
  • Monitor after deploy -- track prediction drift, latency, and error rates
  • Rollback automatically -- don't wait for human intervention on regressions
