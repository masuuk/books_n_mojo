🔌 Interfacing with PyTorch, ONNX, and the MAX Engine

You don't have to throw away your PyTorch models to use Mojo. This chapter shows how Mojo interops with PyTorch directly, how to export models via ONNX, and how the MAX Engine takes inference from Python-speed to native-speed.

Using PyTorch from Mojo

Mojo's Python interoperability layer lets you import and call any Python module directly from Mojo code. This means you can train a model in PyTorch, save it, and then run inference from Mojo without rewriting your model architecture. The Python.import_module function gives you full access to the Python ecosystem.

pytorch_inference.mojo
from python import Python

def main():
    # Import PyTorch directly from Mojo
    var torch = Python.import_module("torch")
    var nn = Python.import_module("torch.nn")

    # Define a simple model
    var model = nn.Linear(128, 10)
    model.eval()  # set to inference mode

    # Create input tensor from Mojo data
    var input_tensor = torch.randn([1, 128])

    # Run inference
    torch.no_grad()
    var output = model(input_tensor)
    var prediction = torch.argmax(output, dim=1)

    print(f"Prediction class: {prediction}")

    # Convert output back to Mojo types
    var scores = output.detach().numpy()
    for i in range(10):
        print(f"  Class {i}: {scores[0][i]:.4f}")

The pure-Python spelling of that same block is import torch / import torch.nn as nn at module scope, with with torch.no_grad(): wrapping the forward pass. The Mojo pane reaches the identical module through Python.import_module("torch") and gets gradient suppression from a bare torch.no_grad() call rather than a context manager.

The Python interop layer is not a toy — it's a fully functional FFI bridge. You can:

  • Call any Python function with automatic type conversion between Mojo and Python types
  • Pass Mojo data structures to Python and get results back without serialization
  • Use Python's GIL safely — Mojo manages the GIL release/acquire cycle automatically when you call into Python
  • Access Python objects as Mojo values — the PythonObject type wraps any Python reference with proper lifetime management
When to use Python interop vs native Mojo

Use Python interop for model training (PyTorch's autograd and ecosystem are unmatched), visualization (matplotlib, seaborn), and data loading (pandas, huggingface datasets). Use native Mojo for inference pipelines, data preprocessing at scale, and production serving where every millisecond counts.

ONNX export and inference

ONNX (Open Neural Network Exchange) is the lingua franca of model deployment. It's a standardized format that describes computation graphs in a way that any runtime can understand. The workflow is straightforward: train in PyTorch, export to ONNX, and run inference in the MAX Engine or any other ONNX runtime.

inference_onnx.mojo
# Run inference in Mojo via MAX Engine
from max.engine import InferenceSession
from math import exp

def softmax(logits: List[Float64]) -> List[Float64]:
    var max_val = logits[0]
    for v in logits:
        if v > max_val:
            max_val = v
    var result = List[Float64](capacity=len(logits))
    var sum_exp: Float64 = 0.0
    for v in logits:
        sum_exp += exp(v - max_val)
    for v in logits:
        result.append(exp(v - max_val) / sum_exp)
    return result

def main():
    # Load the ONNX model into MAX Engine
    var session = InferenceSession("classifier.onnx")

    # Prepare input (e.g., a flattened 28x28 image)
    var input_data = List[Float64](capacity=784)
    for i in range(784):
        input_data.append(Float64(i) / 784.0)

    # Run inference
    var output = session.execute(input_data)
    var probs = softmax(output)

    # Find the predicted class
    var best_idx = 0
    var best_prob = probs[0]
    for i in range(1, len(probs)):
        if probs[i] > best_prob:
            best_prob = probs[i]
            best_idx = i

    print(f"Predicted class: {best_idx} (p={best_prob:.4f})")

The export half of that workflow still happens in Python: a nn.Module subclass whose forward wraps an nn.Sequential(Linear(784, 256), ReLU, Dropout(0.2), Linear(256, 128), ReLU, Linear(128, 10)), then torch.onnx.export(model, dummy, "classifier.onnx", dynamic_axes={"input": {0: "batch"}}, opset_version=17). The dynamic_axes entry is what lets the Mojo pane vary the batch dimension later, and opset_version=17 is the contract the MAX Engine has to honour when it reads the file.

The ONNX format captures not just the model weights but the entire computation graph — every matrix multiply, activation, and reshape operation is encoded in a versioned, cross-platform format. This means you can train on GPU in PyTorch and run inference on CPU, mobile, or edge devices without any code changes.

The MAX Engine for production inference

The MAX Engine is Mojo's native inference runtime. It takes ONNX models (and other formats) and runs them with aggressive compiler optimizations — operator fusion, memory planning, and SIMD vectorization that no Python runtime can match. For data science teams deploying models, this is the path to inference latency that actually meets SLAs.

max_serving.mojo
from max.engine import InferenceSession, Model

def main():
    # Load model with hardware-specific optimizations
    var session = InferenceSession(
        "classifier.onnx",
        dtype=DType.float32,
    )

    # Warmup — first inference compiles the graph
    _ = session.execute(List[Float64](capacity=784))

    # Benchmark inference latency
    var total_time: Float64 = 0.0
    var iterations = 1000

    for i in range(iterations):
        var start = now()
        var _ = session.execute(input_data)
        total_time += (now() - start)

    var avg_ms = (total_time / iterations) * 1000
    print(f"Average latency: {avg_ms:.2f}ms")
    print(f"Throughput: {1000/avg_ms:.0f} inferences/sec")

    # Batch inference for throughput
    var batch_size = 32
    var batch = List[List[Float64]](capacity=batch_size)
    for i in range(batch_size):
        batch.append(create_input(i))

    var batch_output = session.execute_batch(batch)
    print(f"Batch of {batch_size} completed")

The same loop in Python runs through onnxruntime: ort.InferenceSession("classifier.onnx", providers=["CPUExecutionProvider"]), a warmup session.run(None, {"input": input_data}), and time.perf_counter() around the loop. Identical iteration count, identical avg_ms formula — and the number the 3-10x figure in the callout below is measured against.

The MAX Engine automatically selects the best execution strategy for your hardware — AVX-512 on modern x86, NEON on ARM, and GPU acceleration when available. This happens at compile time, not at runtime, so there's no overhead from hardware detection.

⚡ Performance reality check

In benchmarks, the MAX Engine typically delivers 3-10x lower latency than ONNX Runtime on CPU and 2-5x lower latency than PyTorch's native inference. The gap widens with batch size because Mojo's memory model avoids the allocation overhead that Python-based runtimes incur per batch.

Model optimization and quantization

Raw model export isn't enough for production. The MAX Engine provides built-in optimization passes that reduce model size, improve inference speed, and maintain accuracy. Quantization is the most impactful: it converts floating-point weights to lower-precision integers, shrinking the model and speeding up computation with minimal accuracy loss.

optimize_model.mojo
from max.engine import InferenceSession
from max.engine.optimization import (
    quantize_int8,
    quantize_int4,
    fuse_operators,
    optimize_memory,
)

def main():
    # Load model
    var session = InferenceSession("classifier.onnx")

    # Apply optimization pipeline
    var optimized = session.optimize([
        fuse_operators(),       # combine MatMul + Add + ReLU
        optimize_memory(),      # minimize peak allocation
        quantize_int8(),        # INT8 weight quantization
    ])

    # Compare model sizes
    var original_size = session.model_size()
    var optimized_size = optimized.model_size()
    var reduction = (1 - optimized_size / original_size) * 100

    print(f"Original:  {original_size / 1_000_000:.1f} MB")
    print(f"Optimized: {optimized_size / 1_000_000:.1f} MB")
    print(f"Reduction: {reduction:.0f}%")

    # Benchmark the optimized model
    var original_time = benchmark_inference(session, input_data)
    var optimized_time = benchmark_inference(optimized, input_data)

    print(f"Speedup: {original_time / optimized_time:.1f}x")

    # INT4 for edge deployment (more aggressive)
    var edge_model = session.optimize([quantize_int4()])
    print(f"INT4 size: {edge_model.model_size() / 1_000_000:.1f} MB")

The Python equivalent is onnxruntime.quantization.quantize_dynamic(model_input="classifier.onnx", model_output="classifier_int8.onnx", weight_type=QuantType.QInt8), which writes a second file and measures the win with os.path.getsize(...) on both paths — a post-hoc, file-level diff. The pipeline above fuses and re-plans in memory instead, so there is no second artifact to ship.

When NOT to quantize

If your model outputs probabilities that feed into downstream decisions (rather than discrete classifications), quantization noise can cascade. Always validate with your actual production data, not just benchmark datasets. The MAX Engine provides built-in accuracy validation — use it.
