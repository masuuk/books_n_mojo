⏱️ Benchmarking & Profiling

Flame graphs, memory traces, performance analysis, and optimization strategies for Mojo code.

Flame Graphs

Flame graphs are the most intuitive way to visualize where your program spends time. Mojo's built-in profiler generates flame graphs that show call stacks with their relative time proportions — wide bars represent hot functions that dominate execution time.

Mojo 1.x
from profiler import Profiler, FlameGraphConfig

// Start profiling with flame graph output
var profiler = Profiler(
    FlameGraphConfig(
        output="train_flame.svg",
        sample_rate_us=100,  // 100μs sampling
        include_memory=True,
        track_allocations=True
    )
)

profiler.start()
train_model(model, data, epochs=10)
profiler.stop()

// Generate HTML report with interactive flame graph
profiler.report()
// → train_flame.svg + train_report.html

If you are coming from Python, the equivalent workflow is cProfile.run(..., "train.prof") followed by snakeviz train.prof. That path needs an extra tool and a manual conversion step, whereas Mojo emits the flame graph directly.

Interactive Reports

Mojo's profiler generates self-contained HTML files with D3.js-powered flame graphs. You can zoom into specific call stacks, filter by function name, and see both time and allocation breakdowns in a single view.

Reading Flame Graphs

The y-axis shows call stack depth (top = hottest). The x-axis shows the proportion of total time. Key patterns to look for:

  • Wide, flat bars — functions doing real work (expected)
  • Deep stacks — excessive function call overhead (optimize)
  • Narrow bars at the same depth — many functions taking equal time (investigate all)

The Python-side equivalent is tracemalloc, which snapshots allocations and ranks them by source line. It tracks Python object lifetimes only, so it cannot see allocations made inside Mojo's own runtime.

Memory Traces

Memory allocations are often the hidden bottleneck in ML code. Mojo's memory tracer tracks every allocation, its lifetime, and which function requested it. This is especially useful for finding temporary tensors that should be reused.

Mojo 1.x
from profiler import MemoryTracer, MemoryReport

var tracer = MemoryTracer(
    snapshot_interval=1000,  // Every 1000 allocations
    track_lifetime=True,
    detect_leaks=True
)

tracer.start()
var result = model.forward(batch)
tracer.stop()

// Analyze allocation patterns
var report = tracer.report()
print(report.peak_memory_bytes())    // Peak RSS
print(report.allocation_count())      // Total allocations
print(report.temporary_count())       // Allocations freed within 1 step
print(report.leak_count())            // Potential memory leaks

// Show top 10 allocation hotspots
report.top_allocators(n=10)
// → attention.bmm: 847 allocations (2.1 GB)
// → layer_norm.reduce: 512 allocations (128 MB)
Tip: Arena Allocation

If your memory trace shows many small temporary allocations, use Mojo's arena allocator for that computation block. Arenas allocate a single large chunk and free it all at once, eliminating per-allocation overhead.

Memory Optimization Patterns

Mojo 1.x
from memory import ArenaAllocator, arena_scope

// Before: 1000 small allocations per forward pass
def forward_slow(x: Tensor[Float32]) -> Tensor[Float32]:
    var a = x[:, :d_model]       // alloc 1
    var b = self.W_q(a)          // alloc 2
    var c = self.W_k(a)          // alloc 3
    var d = b @ c.transpose()     // alloc 4
    var e = softmax(d)           // alloc 5
    return e @ self.W_v(a)       // alloc 6

// After: single arena allocation, freed at scope end
def forward_fast(x: Tensor[Float32]) -> Tensor[Float32]:
    with arena_scope():
        var a = x[:, :d_model]
        var b = self.W_q(a)
        var c = self.W_k(a)
        var d = b @ c.transpose()
        var e = softmax(d)
        return e @ self.W_v(a)
    // All temporaries freed here

Performance Analysis

Beyond profiling individual functions, you need system-level analysis: hardware counter utilization, memory bandwidth saturation, and vectorization efficiency. Mojo's performance analyzer connects code-level metrics with hardware counters.

Mojo 1.x
from bench import Benchmark, PerfCounter

// Microbenchmark with statistical rigor
var bench = Benchmark(
    name="matmul_4096x4096",
    warmup=100,
    iterations=10000,
    counters=[PerfCounter.FLOPS, PerfCounter.BANDWIDTH_GB]
)

bench.run(def():
    var c = a @ b
)
bench.report()
// → 12.3 TFLOPS (78% of peak)
// → 487 GB/s memory bandwidth (65% of peak)
// → p50: 0.42ms, p99: 0.48ms, p999: 0.51ms

Hardware Counters

Mojo reads Intel PCM and NVIDIA nvidia-smi counters directly, so you don't need separate profiling tools. The PerfCounter enum covers FLOPS, bandwidth, cache misses, branch mispredictions, and GPU SM utilization.

Optimization Strategies

Once you've identified bottlenecks, here are the most common optimization strategies in Mojo:

1. Kernel Fusion

Combine multiple small kernels into one to reduce launch overhead and memory traffic:

Mojo 1.x
from kernel import fused_kernel

// Write a custom fused kernel
@fused_kernel
def bias_gelu_fused(
    output: Tensor[Float32],
    input: Tensor[Float32],
    bias: Tensor[Float32]
):
    var idx = thread_idx_x() + block_idx_x() * block_dim_x()
    if idx < input.size:
        var val = input[idx] + bias[idx % bias.size]
        output[idx] = 0.5 * val * (1.0 + tanh(0.7978845608 * (val + 0.044715 * val ** 3)))

// 3x faster than separate bias + gelu kernels

2. Memory Layout Optimization

Ensure your data layout matches your access pattern:

  • Row-major for batch processing — consecutive batch items in memory
  • Column-major for feature reduction — consecutive features in memory
  • Tiled layouts for convolutions — cache-friendly block access

3. Async Pipeline

Overlap computation with data loading and memory transfers:

Mojo 1.x
from async import Pipeline, Stage

// Pipeline: prefetch → preprocess → compute
var pipeline = Pipeline([
    Stage("load", def(): loader.next_batch(), buffer=4),
    Stage("preprocess", def(b): augment(b), buffer=2),
    Stage("compute", def(b): model.forward(b), buffer=1),
])

// All 3 stages run concurrently on different data
for batch in pipeline:
    loss = loss_fn(batch, targets)
    loss.backward()
Tip: Benchmark Before You Optimize

Never optimize based on intuition alone. Profile first, identify the actual bottleneck, then apply the targeted optimization. Mojo's integrated profiler makes this workflow frictionless.
