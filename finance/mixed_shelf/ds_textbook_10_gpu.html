Part V — GPU Programming · Chapter 10

🎮 Writing GPU Kernels for Training and Inference

Understand GPU architecture — SMs, warps, threads — and write Mojo GPU kernels that accelerate matrix operations, activation functions, and entire training steps beyond what CPU-only code can achieve.

Modern ML runs on GPUs because matrix multiplication — the core operation in neural networks — is embarrassingly parallel. A GPU with thousands of cores can perform thousands of multiply-accumulate operations simultaneously, while a CPU can only do a few at a time. The challenge is that GPU programming requires thinking in terms of threads, blocks, and shared memory — concepts that don't exist in Python.

Mojo makes GPU programming accessible by providing a high-level kernel API that compiles down to the same PTX instructions as hand-written CUDA, but with Mojo's safety guarantees, type system, and comptime features. In this chapter, you'll write GPU kernels for matrix multiplication, vector operations, and a full forward pass — comparing Mojo's approach with CUDA C++ and Python's CuPy.

GPU architecture essentials

Before writing kernels, you need to understand how a GPU executes code. A GPU is organized as a hierarchy of processing units:

  • Streaming Multiprocessors (SMs): Each SM is a self-contained processor with its own registers, shared memory, and thread schedulers. A modern GPU has 20-100+ SMs.
  • Warps: An SM executes threads in groups of 32 called warps. All threads in a warp execute the same instruction simultaneously (SIMT — Single Instruction, Multiple Threads).
  • Thread blocks: A block is a group of threads that can share data through shared memory and synchronize with barriers. Blocks are assigned to SMs.
  • Grid: The grid is the collection of all thread blocks launched by a single kernel call.
GPU hierarchy overview
Grid
├── Block (0,0) ──→ SM 0
│   ├── Thread (0,0)
│   ├── Thread (0,1)
│   ├── ...
│   └── Thread (31,31)  ← 1024 threads per block
├── Block (1,0) ──→ SM 1
│   └── ...
├── Block (0,1) ──→ SM 0  ← SM can run multiple blocks
│   └── ...
└── Block (1,1) ──→ SM 1
    └── ...

Within each SM:
├── 32 warp schedulers
├── Shared memory (up to 48KB per block)
├── Register file (65K+ registers per SM)
└── CUDA cores (FP32/INT32 ALUs)

The key insight for performance: shared memory is fast (100x faster than global memory) but small. Your kernel design must minimize global memory accesses by loading data into shared memory once and reusing it across many computations.

🗄️ Memory hierarchy

Registers (1 cycle) → Shared memory (5-30 cycles) → L1/L2 cache (50-200 cycles) → Global memory (400-800 cycles). A kernel that reads from global memory for every multiply will be 100-800x slower than one that uses shared memory.

Your first Mojo GPU kernel

Mojo 1.x's GPU story splits in two: the device-side built-ins stay in the standard library — from std.gpu import thread_idx, block_idx, block_dim identify each thread's position in the grid — while the host-side APIs (device discovery, memory allocation, kernel launch) moved to the max.gpu package that ships with MAX. A kernel is an ordinary def function that gets compiled to GPU machine code (PTX) and launched through a DeviceContext.

As of Mojo 1.x final

The accelerator APIs left the standard library: std.gpu.host, std.gpu.memory, std.algorithm, and friends are now max.gpu.* and max.algorithm in the MAX accelerator library. Also note: Int and UInt are no longer passable to GPU kernels — use fixed-width types like Int32 for scalar kernel arguments.

kernel.mojo
# Mojo — vector addition GPU kernel (Mojo 1.x / MAX 26.5)
from std.gpu import thread_idx, block_idx, block_dim
from max.gpu.host import DeviceContext, DeviceBuffer
from std.math import ceildiv

comptime BLOCK_SIZE = 256
comptime N = 1_000_000

def vec_add_kernel(a: DeviceBuffer, b: DeviceBuffer,
                   c: DeviceBuffer, n: Int32):
    var tid = block_idx.x * block_dim.x + thread_idx.x
    if tid < n:
        c[tid] = a[tid] + b[tid]

def main() raises:
    var ctx = DeviceContext()

    # Allocate GPU memory (asynchronous, queued on the device stream)
    var d_a = ctx.enqueue_create_buffer[float32](N)
    var d_b = ctx.enqueue_create_buffer[float32](N)
    var d_c = ctx.enqueue_create_buffer[float32](N)
    # ... copy inputs from host with ctx.enqueue_copy(...) ...

    # Compile and launch the kernel on the GPU
    comptime num_blocks = ceildiv(N, BLOCK_SIZE)
    ctx.enqueue_function[vec_add_kernel](
        d_a, d_b, d_c, Int32(N),
        grid_dim=num_blocks, block_dim=BLOCK_SIZE,
    )
    ctx.synchronize()

In CuPy the elementwise case is c = a + b with no launch code at all, and the custom-kernel route means wrapping the same C source in cp.RawModule(code=...).get_function('vec_add') before passing (n//256,), (256,) as the grid and block. Here the kernel is an ordinary Mojo function and its launch sits in the same file.

The Mojo kernel compiles to the same PTX (Parallel Thread Execution) instructions a hand-written CUDA kernel would — and enqueue_function type-checks the kernel's arguments at compile time, so a mismatched argument is a build error, not a runtime crash.

Tiled matrix multiplication with shared memory

Matrix multiplication is the most important GPU kernel in ML. A naive implementation loads each element from global memory many times. The tiled approach loads a block of each matrix into shared memory once, then computes a tile of the output from that shared data — reducing global memory traffic by a factor equal to the tile size.

matmul.mojo
# Mojo — tiled matrix multiplication kernel
from std.gpu import thread_idx, block_idx
from max.gpu.sync import barrier
from std.memory import stack_allocation
from std.memory.address_space import AddressSpace

comptime TILE = 16  # tile size (16x16 = 256 threads)

def matmul_kernel(M: Int32, N: Int32, K: Int32,
                   A: DeviceBuffer, B: DeviceBuffer, C: DeviceBuffer):
    # Shared memory tiles
    var sA = stack_allocation[TILE*TILE, Float32,
        address_space=AddressSpace.SHARED]()
    var sB = stack_allocation[TILE*TILE, Float32,
        address_space=AddressSpace.SHARED]()

    var row = block_idx.y * TILE + thread_idx.y
    var col = block_idx.x * TILE + thread_idx.x
    var sum: Float32 = 0.0

    # Loop over tiles
    var num_tiles = (K + TILE - 1) // TILE
    for t in range(num_tiles):
        # Load tile into shared memory
        var a_col = t * TILE + thread_idx.x
        var b_row = t * TILE + thread_idx.y

        if row < M and a_col < K:
            sA[thread_idx.y * TILE + thread_idx.x] = A[row * K + a_col]
        else:
            sA[thread_idx.y * TILE + thread_idx.x] = 0.0

        if b_row < K and col < N:
            sB[thread_idx.y * TILE + thread_idx.x] = B[b_row * N + col]
        else:
            sB[thread_idx.y * TILE + thread_idx.x] = 0.0

        barrier()  # wait for all threads to load

        # Compute partial dot product from shared memory
        for k in range(TILE):
            sum += sA[thread_idx.y * TILE + k] * sB[k * TILE + thread_idx.x]

        barrier()  # wait before loading next tile

    # Write result to global memory
    if row < M and col < N:
        C[row * N + col] = sum

# Launch: grid of tiles, block of TILE x TILE threads
var grid = ((N + TILE - 1) // TILE, (M + TILE - 1) // TILE)
ctx.enqueue_function[matmul_kernel](
    Int32(M), Int32(N), Int32(K), d_A, d_B, d_C,
    grid_dim=grid, block_dim=(TILE, TILE),
)

From Python the same multiply is C = A @ B on CuPy device arrays, or torch.randn(M, K, device='cuda') followed by the same @ — either way it dispatches to a vendor GEMM, which is the cuBLAS row in the table below. Reaching that last row's level of control in Python means Triton or a hand-written CUDA extension; in Mojo it is the kernel above.

Why tiled matmul is faster

Without tiling, each element of A is read from global memory K times (once per column of B). With 16x16 tiles, each element is read once into shared memory and reused 16 times. For a 1024x1024 matrix multiply, this reduces global memory reads from 2 billion to 128 million — a 16x reduction in memory traffic.

GPU-accelerated activation functions

Activation functions like ReLU, sigmoid, and softmax are element-wise operations — each thread handles one element. These are the simplest GPU kernels to write but are critical for training performance because they appear in every layer of a network.

activation kernels in Mojo
# Element-wise ReLU kernel
def relu_kernel(x: DeviceBuffer, y: DeviceBuffer, n: Int32):
    var tid = block_idx.x * block_dim.x + thread_idx.x
    if tid < n:
        y[tid] = max(x[tid], 0.0)

# Element-wise sigmoid kernel
def sigmoid_kernel(x: DeviceBuffer, y: DeviceBuffer, n: Int32):
    var tid = block_idx.x * block_dim.x + thread_idx.x
    if tid < n:
        y[tid] = 1.0 / (1.0 + exp(-x[tid]))

# Batched softmax (more complex — needs reduction)
def softmax_kernel(x: DeviceBuffer, y: DeviceBuffer,
                   rows: Int32, cols: Int32):
    var row = block_idx.x * block_dim.x + thread_idx.x
    if row >= rows:
        return

    # Find max for numerical stability
    var row_max: Float32 = x[row * cols]
    for j in range(1, cols):
        row_max = max(row_max, x[row * cols + j])

    # Compute exp and sum
    var row_sum: Float32 = 0.0
    for j in range(cols):
        var val = exp(x[row * cols + j] - row_max)
        y[row * cols + j] = val
        row_sum += val

    # Normalize
    for j in range(cols):
        y[row * cols + j] /= row_sum

# Launch: one thread per row for softmax
ctx.enqueue_function[softmax_kernel](
    d_x, d_y, Int32(rows), Int32(cols),
    grid_dim=num_blocks, block_dim=256,
)
⚡ Performance tip

For element-wise kernels (ReLU, sigmoid), each thread does very little work. The bottleneck is memory bandwidth — loading the data costs more time than computing the result. Use vectorized loads (loading 4 or 16 floats at once) to maximize memory throughput. Mojo's SIMD type makes this natural: just load a SIMD[float32, 8] instead of individual floats.
