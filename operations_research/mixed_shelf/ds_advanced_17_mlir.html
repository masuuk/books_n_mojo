🔩 Inline MLIR

Mojo is built on MLIR and exposes it directly. When you need an operation Mojo doesn't surface — hardware intrinsics, atomic memory orderings, custom dialect ops — you can write the MLIR yourself instead of waiting for a language feature.

1. Hello MLIR

MLIR (Multi-Level Intermediate Representation) is a compiler framework in the LLVM project. It models programs with custom, layered dialects that represent data flow, loops, and hardware-specific operations, translated step by step into LLVM IR and then machine code.

This minimal example creates two MLIR index constants, adds them, and converts the result back to Mojo's Int:

Mojo
output
def main():
    var a: __mlir_type.index = __mlir_attr.`42 : index`
    var b: __mlir_type.index = __mlir_attr.`8 : index`
    var c = __mlir_op.`index.add`(a, b)
    print(Int(mlir_value=c))   # 50
50
Why not just write 42 + 8?

You could. Inline MLIR gives you direct access to operations that Mojo doesn't expose yet, such as NVVM barriers, AMD matrix multiplies, and target-specific address spaces — the bedrock of hand-tuned GPU kernels.

2. The Four Built-in Identifiers

Each built-in corresponds to a common MLIR building block:

Built-inPurposeProduces
__mlir_typeReference an MLIR typeA type
__mlir_attrReference an MLIR attributeCompile-time value
__mlir_opInvoke an MLIR operationRuntime value or None
__mlir_regionDefine a single-block regionStatement (no value)

Types and attributes support two forms: dot/backtick syntax for simple names, and bracket syntax for parameterized construction. Raw MLIR types are register-passable, trivially copyable, and trivially movable — but they have no methods, and .field access on them is an error.

3. Types & Attributes

__mlir_type

Use dot syntax for simple names, backticks when the name includes special characters like !, <, or >:

Mojo
var x: __mlir_type.i1                        # 1-bit integer (boolean)
var y: __mlir_type.index                     # Machine-width index
var z: __mlir_type.f64                        # 64-bit float
var a: __mlir_type.`!kgen.none`            # Dialect type with ! prefix
var b: __mlir_type.`!kgen.scalar<f64>`   # Pop dialect scalar

def mlir_types_in_action():
    var flag: __mlir_type.i1 = __mlir_attr.true
    var count: __mlir_type.index = __mlir_attr.`0 : index`
    print(Bool(flag))                    # True
    print(Int(mlir_value=count))       # 0

The names you'll see most: i1 (boolean), i32/i64 (signless integers — the operation decides signedness), si32/ui32 (signedness in the type), f16/bf16/f32/f64, and index for sizes and offsets. Dialect-defined types use the ! prefix — without it, the compiler rejects the type.

Bracket syntax — compile-time splicing

Bracket syntax builds a type or attribute from values known at compile time. The list alternates backtick literals (copied as-is) and Mojo expressions (inserted as MLIR text):

Mojo
# From SIMD: for SIMD[DType.float32, 4] produces: !kgen.simd<4, f32>
comptime _mlir_type = __mlir_type[
    `!kgen.simd<`, Self.size._mlir_value, `,`,
    Self.dtype._mlir_value, `>`]

# Nested substitution: produces complex<i32>
var complex_int: __mlir_type[`complex<`, __mlir_type.i32, `>`]

MLIR types can even serve as compile-time parameters — a !kgen.string or !kgen.dtype parameter list entry is plain Mojo parameterization over MLIR values. Bracket lists accept positional operands only; keyword operands are a compile-time error.

__mlir_attr

Attributes are compile-time constants embedded in the IR. Typed constants use backtick syntax with MLIR literal notation — not Mojo's: binary, octal, and hex prefixes aren't supported, so use decimal values:

Mojo
# Boolean attributes and builtin type shorthands
__mlir_attr.true
__mlir_attr.false
__mlir_attr.i1
__mlir_attr.index

# Typed constants (backtick syntax)
__mlir_attr.`0 : index`
__mlir_attr.`42 : i17`
__mlir_attr.`1 : si32`

# Dialect-specific attributes
__mlir_attr.`#kgen.dtype.constant<f32> : !kgen.dtype`  # f32 constant
__mlir_attr.`#index<cmp_predicate slt>`                  # Signed less-than
__mlir_attr.`#pop<atomic_ordering seq_cst>`              # Seq-cst ordering

4. Operations: __mlir_op

Compile-time parameters (attributes) go in square brackets; runtime values (operands) go in parentheses; the operation name sits in backticks:

Mojo
output
def clamp(val: Int, low: Int, high: Int) -> Int:
    """Clamp val to [low, high] using MLIR comparisons and select."""
    var v = val.__mlir_index__()
    var lo = low.__mlir_index__()
    var hi = high.__mlir_index__()

    # index.cmp returns i1, but pop.select needs !kgen.scalar<bool>
    var too_low = __mlir_op.`pop.cast_from_builtin`[
        _type=__mlir_type.`!kgen.scalar<bool>`](
        __mlir_op.`index.cmp`[pred=__mlir_attr.`#index<cmp_predicate slt>`](v, lo))
    var result = __mlir_op.`pop.select`(too_low, lo, v)

    var too_high = __mlir_op.`pop.cast_from_builtin`[
        _type=__mlir_type.`!kgen.scalar<bool>`](
        __mlir_op.`index.cmp`[pred=__mlir_attr.`#index<cmp_predicate sgt>`](result, hi))
    result = __mlir_op.`pop.select`(too_high, hi, result)
    return Int(mlir_value=result)

def main():
    print(clamp(15, 0, 10))   # 10
    print(clamp(-5, 0, 10))   # 0
    print(clamp(7, 0, 10))    # 7
10
0
7

Special attributes

AttributePurpose
_typeSets the result type; pass None for an operation with no result
_propertiesPasses MLIR operation properties as a DictionaryAttr
_regionReferences a named __mlir_region as a region argument

Most operations require an explicit _type; if the compiler can't infer the result type and you don't provide it, you get "unable to infer result type from MLIR operation". Multi-result operations assign to a typed tuple, and operations that produce no result — like an NVVM fence after mbarrier initialization — take _type=None:

Mojo
# Current source location as (line, column, filename)
_ = __mlir_op.`kgen.source_loc`[
    _type=(__mlir_type.index, __mlir_type.index,
           __mlir_type.`!kgen.string`),
    _properties=__mlir_attr.`{inlineCount = 1 : i64}`,
]()

# Fence after mbarrier init: no result
__mlir_op.`nvvm.fence.mbarrier.init`[_type=None]

You can only call registered MLIR operations — anything else errors with "use of unregistered MLIR operation".

5. Regions: __mlir_region

A region is a block of code an MLIR operation runs — like a loop body or callback. Unlike a closure, it doesn't implicitly capture variables. Define it as a named block with arguments and an indented body, then pass it by name via _region:

Mojo
output
# Mojo while loop for control flow, MLIR for the computation inside
def sum_to(end: Int) -> Int:
    var acc: __mlir_type.index = __mlir_attr.`0 : index`
    var i: __mlir_type.index = __mlir_attr.`0 : index`
    var one: __mlir_type.index = __mlir_attr.`1 : index`

    while Bool(__mlir_op.`index.cmp`[
        pred=__mlir_attr.`#index<cmp_predicate slt>`](i, end.__mlir_index__())):
        acc = __mlir_op.`index.add`(acc, i)
        i = __mlir_op.`index.add`(i, one)

    return Int(mlir_value=acc)

def main():
    print(sum_to(10))   # 45
45

Region arguments look like function arguments but don't support Mojo conventions (ref, var, mut) — the operation provides raw MLIR values, which you wrap (e.g. Int(mlir_value=x)) before using Mojo operations on them. A function can define multiple regions, each a single block, referenced by name.

💡 Tip:

In practice it's simpler to use Mojo's for and while loops for control flow and reach for __mlir_region only when an operation demands one — like coroutine co.suspend bodies.

6. Common Dialects

PrefixCovers
pop.*Mojo portable ops: arithmetic, casts, SIMD, pointers
index.*Index-typed arithmetic and comparisons
kgen.*Codegen primitives: structs, variants, parameters
lit.*Language-level ops: ownership, references, closures
llvm.*LLVM dialect: traps, inline assembly, pointer ops
nvvm.*NVIDIA GPU intrinsics: barriers, async copies, tensor ops
co.*Coroutine ops: suspend, resume, destroy, await

The pop, kgen, co, and lit dialects are internal compiler implementation details and may change without notice; built-in dialects like index are stable.

7. Stdlib Patterns: Wrapper Structs

The standard library uses inline MLIR in one dominant pattern: a Mojo struct wraps a raw MLIR type in a field called _mlir_value — the struct provides a Mojo-friendly interface, the field holds the hardware value. Bool wraps a single bit this way; SIMD, UnsafePointer, Tuple, Variant, and Optional all use the same shape.

Mojo
output
struct Counter:
    """A counter with addition, backed by a raw MLIR index."""
    var _mlir_value: __mlir_type.index

    def __init__(out self):
        self._mlir_value = __mlir_attr.`0 : index`

    def __init__(out self, *, mlir_value: __mlir_type.index):
        self._mlir_value = mlir_value

    def increment(mut self):
        var one: __mlir_type.index = __mlir_attr.`1 : index`
        self._mlir_value = __mlir_op.`index.add`(self._mlir_value, one)

    def __add__(self, rhs: Counter) -> Counter:
        return Counter(mlir_value=__mlir_op.`index.add`(
            self._mlir_value, rhs._mlir_value))

    def value(self) -> Int:
        return Int(mlir_value=self._mlir_value)

def main():
    var a = Counter()
    a.increment()   # 1
    a.increment()   # 2
    var b = Counter()
    b.increment()   # 1
    var c = a + b
    print(c.value())   # 3
3

Methods delegate to MLIR operations — _mlir_value goes in, the result comes back, and the struct re-wraps it. When the storage type depends on struct parameters (as with SIMD's dtype and size), define it as a comptime alias with bracket syntax.
