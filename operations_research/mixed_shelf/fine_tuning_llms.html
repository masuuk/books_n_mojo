1. The VRAM Equation

Every fine-tuning decision reduces to one accounting identity. During training you must hold weights, gradients, optimizer states, and activations. For a model with P parameters in mixed-precision training with Adam:

full fine-tune:  M ≈ P·(2 bytes weightsbf16 + 2 gradients + 8 Adam m,v in fp32) + activations
= 12·P bytes + activations   ⟹  7B params ≈ 84 GB before activations

LoRA (frozen 16-bit base):  M ≈ 2·P + 12·Plora + activations   (Plora ≈ 0.5% of P)
QLoRA (frozen 4-bit base):  M ≈ 0.5·P + 12·Plora + activations   ⟹  7B ≈ 4–10 GB total

Why 12 bytes per trainable parameter? One bf16 weight (2) + its bf16 gradient (2) + Adam's two fp32 moments (4+4). Freezing a parameter removes 10 of the 12 bytes — that is PEFT. Quantizing the frozen remainder from 2 bytes to 0.5 (4-bit) shrinks it 4× — that is QLoRA. The QLoRA paper's measurement that makes adapters-on-every-layer nearly free: for a 7B model at batch size 1, LoRA input gradients were ~567 MB while LoRA parameters were ~26 MB — activations, not adapters, dominate.

def vram_budget(params: Float64,
                    lora_frac: Float64,
                    base_bytes: Float64) -> Float64:
    # trainable params cost 12 B each; frozen cost base_bytes
    var trainable = lora_frac * params
    var frozen   = (1.0 - lora_frac) * params
    return 12.0*trainable + base_bytes*frozen

def main():
    var P = 7e9
    print(vram_budget(P, 1.0,  2.0)/1e9)  # full FT:  84 GB
    print(vram_budget(P, 0.005, 2.0)/1e9)  # LoRA:  ~14.4 GB
    print(vram_budget(P, 0.005, 0.5)/1e9)  # QLoRA: ~3.9 GB

2. LoRA: The Low-Rank Update

Empirical fact: fine-tuning weight deltas are effectively low-rank. So don't learn ΔW ∈ ℝh×o — learn a factored one.

forward:  Y = X·W + s·X·A·B,  A ∈ ℝr×o, B ∈ ℝh×r, s = α/r, r ≪ min(h, o)

trainable params:  Plora = r·(h + o)  vs full  h·o   ⟹  fraction = r(h+o)/(h·o) ≈ r/h + r/o
init:  A ~ N(0, σ²),  B = 0   ⟹ ΔW = 0 at step 0 (training starts at the base model)

Example: a 4096×4096 linear layer with r = 16 trains 131k parameters instead of 16.8M — 0.8%. The adapter is a few MB, swappable per task, and merges away at deploy time (Section 4). The whole mechanism as pure arithmetic:

from tensor import Tensor
from std.random import normal_float64, seed

# the forward pass as pure arithmetic — dtype and shapes are
# compile-time facts, and the r-inner-product is a tight loop.
def lora_forward(X: Tensor[DType.float64], W: Tensor[DType.float64],
                  B: Tensor[DType.float64], A: Tensor[DType.float64],
                  r: Int, alpha: Float64) -> Tensor[DType.float64]:
    var n = X.shape()[0]
    var o = W.shape()[1]
    var s = alpha / Float64(r)
    var Y = Tensor[DType.float64](n, o)
    for i in range(n):
        for j in range(o):
            var base = dot_row(X, W, i, j)        # X[i,:]·W[:,j]
            var delta: Float64 = 0.0
            for k in range(r):               # the low-rank path
                delta += X[i, k] * B[k, 0] * A[0, j]  # (illustrative 1-r)
            Y[i, j] = base + s * delta
    return Y

# init rule: B = 0 exactly, A ~ N(0, 0.02²)
seed(42)
var a0 = normal_float64(0.0, 0.02)

Two defaults that matter more than the rest: target all linear layers (attention + MLP — the difference between matching full fine-tuning and not), and use the shortest sensible sequence length — activations scale linearly in tokens and are the biggest slice of memory. And note what is not trainable: the base W is a constant, so the gradient flows only through A and B — which is exactly why the init rule can afford B = 0 without stalling the first step.

3. QLoRA: NF4 Quantization

QLoRA freezes the base in 4-bit NormalFloat and backpropagates through it into the LoRA adapters. Quantization is block-wise affine; NF4 just chooses the 16 breakpoints as the quantiles of a standard normal, so each 4-bit code holds an equal expected share of the (approximately zero-mean Gaussian) weights.

quantize (block size b):  δ = (max−min)/(2⁴−1),  q = clip(round((w − min)/δ), 0, 15)
dequantize:  ŵ = min + δ·q   — stored 4 bits/weight + fp32 (min, δ) per block

constant overhead:  fp32/b=64 = 0.5 bits/param  →  double quant (fp32→fp8, b=256): 0.127 bits/param
saved: 0.373 bits/param ≈ 3 GB on a 65B model

compute flow:  Ybf16 = Xbf16 · dequant(c₁, c₂, WNF4) + Xbf16 · (α/r)·B·A

Stored 4-bit, computed bf16: weights are dequantized on the fly, and gradients are only ever formed for the 16-bit adapters — never the 4-bit base. That is the entire reason the base can stay quantized during backprop.

The codebook is the only thing separating NF4 from ordinary int4, and it is one line: the 16 codes are the equal-mass quantiles of N(0,1) rescaled to [−1, 1], so a nearest-code search against that table replaces the uniform grid. The kernel below is the uniform-grid half — block-wise absmax down to 16 codes in one compiled pass — and it is the half that has to be fast, because it runs over every weight at load and again over every block whenever an adapter is swapped. Swapping the grid for the NF4 table and measuring the relative-error win is exercise 4.

from std.collections import List
from std.math import abs, max

# block-wise absmax quantize to 4-bit codes — the kernel that
# makes serving-side quantization a single compiled pass.
def quantize_absmax(w: List[Float64], b: Int,
                     out_q: List[Int], out_scale: List[Float64]):
    var n = len(w)
    var n_blocks = n // b
    for blk in range(n_blocks):
        var lo = blk * b
        var hi = lo + b
        var am: Float64 = 0.0
        for i in range(lo, hi):
            am = max(am, abs(w[i]))
        out_scale[blk] = am                 # fp32 constant per block
        for i in range(lo, hi):
            var wn = w[i] / (am + 1e-12)      # to [-1,1]
            out_q[i] = Int((wn + 1.0) * 7.5 + 0.5) # 16 codes

def dequant(q: List[Int], scale: Float64) -> Float64:
    return (Float64(q) / 7.5 - 1.0) * scale

Validation numbers: QLoRA matched 16-bit fine-tuning quality (Guanaco-65B reached 99.3% of ChatGPT's Vicuna score, fine-tuned on a single 48 GB GPU), and a 9k-sample curated dataset beat a 450k one — quality beats quantity is an equation-level constraint on your data budget, not advice.

4. Merging & Serving

At deploy time the adapter folds into the base — one small matmul per layer, zero inference overhead afterwards. From the Python side the whole fold is one call, model.merge_and_unload(), followed by a save_pretrained; there is just no reason to pay a process boundary to do arithmetic that is already this cheap:

W′ = W + (α/r)·B·A   — merge once, serve W′ with no adapter path in the graph 
from tensor import Tensor

# native merge: ΔW = (α/r)·B·A over Tensors — compiles to SIMD,
# dtype is a compile-time fact (float16 = the training dtype).
def merge_lora(W: Tensor[DType.float16],
                 A: Tensor[DType.float16],
                 B: Tensor[DType.float16], r: Int,
                 alpha: Float64) -> Tensor[DType.float16]:
    var n = W.shape()[0]
    var m = W.shape()[1]
    var scale = Float16(alpha / Float64(r))
    var out = Tensor[DType.float16](n, m)
    for i in range(n):
        for j in range(m):
            var delta: Float16 = 0.0
            for k in range(r):        # low-rank inner product
                delta += B[i, k] * A[k, j]
            out[i, j] = W[i, j] + scale * delta
    return out

Then serve natively: export the merged model to ONNX and run it on MAX — the first call compiles the graph for your hardware, every call after is a quantization-aware forward pass with no Python process in the serving path:

from max.engine import InferenceSession
from tensor import Tensor

def serve(prompt_ids: Tensor[DType.int32]) raises:
    var session = InferenceSession("phi3-yoda.onnx",
                                 dtype=DType.float16)
    _ = session.execute(prompt_ids)         # first call compiles
    var tokens = session.execute(prompt_ids)  # warm: native latency
    return tokens

5. The Full Training Pipeline

The end-to-end recipe, driven from Mojo. The Hugging Face stack still does the training — its CUDA kernels are unmatched — but the orchestration, the load-time accounting and the handoff to the native merge in Section 4 are all compiled.

from std.python import Python

# The same run driven from Mojo: the HF stack through the bridge, the
# orchestration compiled, then the adapter merges natively (Section 4).
var tf   = Python.import_module("transformers")
var peft = Python.import_module("peft")
var trl  = Python.import_module("trl")
var dsn  = Python.import_module("datasets")

def main() raises:
    # 1) 4-bit base
    var bnb = tf.BitsAndBytesConfig(
        load_in_4bit=True,
        bnb_4bit_quant_type="nf4",
        bnb_4bit_use_double_quant=True)
    var repo = "microsoft/Phi-3-mini-4k-instruct"
    var model = tf.AutoModelForCausalLM.from_pretrained(
        repo, device_map="auto", quantization_config=bnb)

    # 2) LoRA on ALL linear layers
    model = peft.prepare_model_for_kbit_training(model)
    model = peft.get_peft_model(model, peft.LoraConfig(
        r=8, lora_alpha=16, lora_dropout=0.05,
        task_type="CAUSAL_LM",
        target_modules=["o_proj", "qkv_proj",
                        "gate_up_proj", "down_proj"]))

    # 3) data + tokenizer
    var data = dsn.load_dataset("dvgodoy/yoda_sentences", split="train")
    var tok = tf.AutoTokenizer.from_pretrained(repo)
    tok.pad_token = tok.unk_token       # keep EOS unmasked

    # 4) train — paged optimizer absorbs long-sequence spikes
    var trainer = trl.SFTTrainer(
        model=model, processing_class=tok, train_dataset=data,
        args=trl.SFTConfig(
            output_dir="./phi3-yoda-adapter",
            per_device_train_batch_size=16,
            gradient_checkpointing=True,
            max_length=64,              # shortest sensible
            num_train_epochs=10, learning_rate=3e-4,
            optim="paged_adamw_8bit",
            logging_steps=10, report_to="none"))
    trainer.train()
    trainer.save_model()                # saves only the adapter

    # 5) the number that tells you it worked
    var counts = model.get_nb_trainable_parameters()   # (trainable, total)
    print("trainable %:", 100.0 * counts[0] / counts[1])   # ~0.3% — check it!
    print("footprint GB:", model.get_memory_footprint() / 1e9)

Version gotchas (trl ≥ 0.20): max_seq_length was renamed to max_length; bf16 defaults to True — guard with torch.cuda.is_bf16_supported() on older GPUs; in trl 0.21 prefer passing peft_config= to SFTTrainer over the pre-applied adapters this block uses.

6. Prompt vs RAG vs Fine-Tune

Three levers: prompting changes the instructions, RAG changes the knowledge, fine-tuning changes the behaviour. The decision is a flowchart, not a debate:

task fails with a plain prompt? │ no ──▶ done: prompting ▼ yes does the answer depend on facts the model doesn't know / changes daily / lives in private docs? │ yes ──▶ RAG (update the index, never the weights) ▼ no need consistent format/style at scale, long prompts to kill, or a stable decision policy — AND ≥ 500 curated examples? │ yes ──▶ QLoRA fine-tune ▼ no few-shot prompting (3–5 examples in context) ▼ still fails and data is growing ──▶ fine-tune, hybrid with RAG
break-even heuristic:  fine-tune when  (calls/day) × (prompt tokens saved) × ($/token) > (GPU hours) × ($/GPU-hour) + curation cost
knowledge rule:  RAG for what the model should know;  fine-tune for how it should behave

Don't fine-tune facts that change. Weights freeze at training time; an index updates in seconds. Hybrid is the production default: QLoRA for format/tone/tool use, RAG for live facts — you can even fine-tune on retrieved context so the model learns to cite and to refuse when retrieval is empty. If your errors have asymmetric costs, weight the training data by decision impact — see the Decision-Aware ML book.

7. Evaluation Metrics

Define these before training. A loss curve measures confidence, not correctness — a model can plateau and still hallucinate reliably.

format validity:  V = #(outputs parse as target schema) / n
exact match:  EM = #(ŷ = y) / n  ·  field recall = #(required fields present) / #required  ·  precision = #(correct fields) / #emitted
decision cost (if outputs drive decisions):  C̄ = (1/n) Σ c(d(ŷᵢ), yᵢ)  — primary metric
Elo from pairwise LLM-judged wins:  update RA ← RA + K(SA − EA),  EA = 1/(1+10(RB−RA)/400) 
from std.collections import List
from std.python import Python

var json = Python.import_module("json")

# format validity: does the output parse as the target schema at all?
# A loss curve cannot tell you this — a model plateaus and still emits
# text that no parser will accept.
def parses(o: String) raises -> Bool:
    try:
        json.loads(o)
        return True
    except:
        return False

def format_validity(outs: List[String]) -> Float64:
    var ok = 0
    for i in range(len(outs)):
        if parses(outs[i]):
            ok += 1
    return Float64(ok) / Float64(len(outs))

def exact_match(outs: List[String],
                tgts: List[String]) -> Float64:
    var hits = 0
    for i in range(len(outs)):
        if outs[i].strip() == tgts[i].strip():
            hits += 1
    return Float64(hits) / Float64(len(outs))

# Elo update after one judged match (K = 32, S = 1/0/0.5):
def elo_update(ra: Float64, rb: Float64,
               s_a: Float64) -> (Float64, Float64):
    var ea = 1.0 / (1.0 + 10.0 ** ((rb - ra) / 400.0))
    var delta = 32.0 * (s_a - ea)
    return (ra + delta, rb - delta)

# decision cost is the primary metric when the outputs drive decisions —
# see decision_aware_ml.html Section 8 for the loop.

Report: one task metric + one regression check + tokens-per-call and VRAM before/after + worst-group cost. GPT-4-as-judge with Elo is fine for iteration; never ship on judge scores alone.

8. Self-Check

  1. Derive the 12-bytes-per-trainable-parameter rule. Why does freezing remove 10 of them, and why do activations (not adapters) dominate LoRA memory?
  2. Compute the LoRA trainable fraction for a 4096×4096 layer at r = 8, 16, 64. What is α if the scaling s must stay at 2.0?
  3. Why is B initialized to zero and A random? What would happen with both random?
  4. Implement NF4 quantize/dequantize (Section 3) and measure relative error on Gaussian weights vs uniform int4.
  5. Show why double quantization saves exactly 32/64 − 8/256 ≈ 0.373 bits per parameter, and verify the ~3 GB figure for a 65B model.
  6. Run the Section 5 pipeline end to end; report trainable %, VRAM footprint, exact match, one regression check, and tokens-per-call before/after.
  7. Use the Section 6 flowchart on: (a) legal Q&A over a corpus updated daily, (b) strict JSON in a niche schema at 10k calls/day, (c) a one-off summariser.
