🚀 Inference & Deployment

Graph compilation, quantization, MojoServe, and model export for production ML systems.

Graph Compilation

Training frameworks like PyTorch use eager execution — each operation runs immediately. For inference, this overhead adds up. Mojo's graph compiler traces the computation graph, fuses operations, and generates optimized machine code for your target hardware.

The compiler performs several critical optimizations: operator fusion (combining elementwise ops into a single kernel), constant folding (evaluating expressions at compile time), and dead code elimination (removing unused computations).

Mojo 1.x
from compiler import compile_model, CompileConfig
from inference import InferenceSession

// Compile a trained model for inference
var cfg = CompileConfig(
    target=Target.CPU,   // or Target.CUDA, Target.METAL
    precision=Float16,
    fuse_ops=True,
    optimize_memory=True
)

var compiled = compile_model(
    model_path="model.mojomodel",
    config=cfg
)

// Run inference — no Python overhead
var session = InferenceSession(compiled)
var output = session.run(input_tensor)
print(output.shape)  // [1, 512, 1024]
MLIR-Powered

Mojo's compiler builds on MLIR (Multi-Level Intermediate Representation), the same infrastructure used by TensorFlow and JAX. This means you get hardware-specific optimizations for CPU, GPU, and TPU from a single compilation step.

Fusion Patterns

The compiler automatically identifies fusible operations. Common patterns that get fused:

  • LayerNorm + Dropout — single kernel instead of two
  • Bias + GELU — eliminates intermediate memory allocation
  • MatMul + Add + Reshape — fused attention kernel
Mojo 1.x
// The compiler sees this sequence:
var x = matmul(q, k_transposed)
var x = x / sqrt(d_k)
var x = softmax(x, axis=-1)
var x = matmul(x, v)

// And compiles it into a single fused attention kernel
// No intermediate tensors allocated on the heap

// You can inspect the fusion report:
compiled.fusion_report()
// → "Fused 4 ops into 1 kernel (attention)
//    Memory saved: 3 allocations eliminated
//    Speedup: 2.3x vs unfused"

Quantization

Quantization reduces model size and latency by representing weights and activations with lower-precision integers. Mojo provides calibration-based quantization with per-layer precision selection.

Mojo 1.x
from quantize import QuantConfig, quantize_model, CalibrationData

// INT8 dynamic quantization with calibration
var qcfg = QuantConfig(
    dtype=Int8,
    method=Method.DYNAMIC,
    calibration=CalibrationData.from_dataset(
        val_data, num_samples=1000
    )
)

// Quantize — preserves accuracy with calibration
var quantized = quantize_model(model, qcfg)
print(quantized.size_bytes())  // ~75% reduction

// Mixed precision: keep sensitive layers at FP16
quantized.set_precision("attention.qkv", Float16)
quantized.set_precision("output_head", Float32)

Quantization Strategies

Tip: Accuracy Validation

Always run your quantized model against a held-out validation set. Mojo's quantize_model returns an accuracy report alongside the quantized model, showing per-layer sensitivity scores.

MojoServe

MojoServe is a high-performance inference server built in pure Mojo. It supports OpenAI-compatible API endpoints, batching, streaming, and multi-model serving — all with sub-millisecond latency overhead.

Mojo 1.x
from serve import Server, ModelConfig, BatchingConfig

// Load and serve a compiled model
var model_cfg = ModelConfig(
    path="./compiled_model.mojomodel",
    max_batch_size=32,
    timeout_ms=50
)

var server = Server(
    models=[model_cfg],
    port=8080,
    batching=BatchingConfig(
        strategy=Strategy.DYNAMIC,
        max_wait_ms=5
    ),
    auth=AuthConfig(api_keys=["sk-..."])
)

// Start serving — OpenAI-compatible API
server.start()
// POST /v1/chat/completions
// POST /v1/embeddings
// GET  /v1/models
Dynamic Batching

MojoServe collects incoming requests for up to 5ms and batches them together, maximizing GPU utilization. This is similar to NVIDIA Triton's dynamic batching but implemented entirely in Mojo with zero Python overhead.

Health & Monitoring

MojoServe exposes Prometheus metrics and health endpoints out of the box:

  • /health — liveness and readiness checks
  • /metrics — request latency, throughput, queue depth, GPU utilization
  • /v1/models — model metadata and version info

Model Export

Moving models between frameworks is a persistent pain point. Mojo supports standard formats (ONNX, SafeTensors) plus its own .mojomodel format that embeds the computation graph, weights, and metadata in a single file.

Mojo 1.x
from export import export_model, ExportFormat

// Export to Mojo's native format
export_model(
    model,
    path="./model.mojomodel",
    format=ExportFormat.MOJO,
    sample_input=example_batch
)

// Export to ONNX for cross-framework compatibility
export_model(
    model,
    path="./model.onnx",
    format=ExportFormat.ONNX,
    opset_version=17
)

// Export weights only (SafeTensors)
export_model(
    model,
    path="./weights.safetensors",
    format=ExportFormat.SAFETENSORS
)
Tip: Cross-Framework Interop

The .mojomodel format includes a model card with input/output specs, precision requirements, and hardware recommendations. This metadata makes it easy to deploy models without manual configuration.
