📐 Autodiff and Compile-Time Metaprogramming

Harness Mojo's automatic differentiation and comptime evaluation to write code that transforms itself at compile time — producing specialized, zero-overhead implementations for every data type and shape.

Two features separate Mojo from every other language in the ML space: reverse-mode automatic differentiation built into the type system, and comptime metaprogramming that lets you generate specialized code at compile time. Together, they let you write generic algorithms that compile down to the same hand-tuned code you'd write by hand for each specific use case.

If you've used JAX's grad or PyTorch's autograd, you know autodiff. Mojo's version is different: it's not a runtime wrapper that traces a computation graph. It's a compiler pass that inserts gradient computation directly into the generated code, eliminating the graph overhead entirely. And comptime means you can generate different code for different tensor shapes, types, or hardware targets — all without runtime branching.

Automatic differentiation in Mojo

Mojo supports reverse-mode autodiff through the grad function and the @differentiable decorator. When you mark a function as differentiable, Mojo's compiler automatically generates the backward pass that computes gradients with respect to function arguments. No manual gradient coding needed.

autodiff.mojo
# Mojo — built-in autodiff
from math import exp, log

@differentiable
def quadratic(x: Float64) -> Float64:
    return x * x + 2.0 * x + 1.0

# Compute the derivative at x = 3.0
var df = grad(quadratic)
var slope = df(3.0)   # 2*3 + 2 = 8.0
print(slope)            # 8.0

# Multi-variable differentiation
@differentiable
def loss_fn(w: Float64, b: Float64) -> Float64:
    var pred = w * 3.0 + b
    return (pred - 5.0) ** 2

var grad_fn = grad(loss_fn)
var (dw, db) = grad_fn(1.0, 0.0)
print(f"dW = {dw}, db = {db}")
# dW = -12.0, db = -4.0

# Composing differentiable functions
@differentiable
def sigmoid(x: Float64) -> Float64:
    return 1.0 / (1.0 + exp(-x))

@differentiable
def bce(pred: Float64, target: Float64) -> Float64:
    var p = sigmoid(pred)
    return -(target * log(p) + (1.0 - target) * log(1.0 - p))

var grad_bce = grad(bce)
var gradient = grad_bce(0.5, 1.0)

JAX spells the same two functions jax.grad(quadratic) and jax.grad(loss_fn, argnums=(0, 1)) — the delta is not the API, it is when the derivative is worked out.

How Mojo's autodiff works

When you write @differentiable, Mojo's compiler does two things:

  • Forward pass: The original function compiles normally — there's zero overhead when you don't call grad.
  • Backward pass: When you call grad(fn), the compiler generates a second function that computes the derivative of every intermediate expression using the chain rule. This happens at compile time, not at runtime.

Compare this with JAX, which traces Python execution into a jaxpr graph at runtime, then compiles that graph. Mojo's approach has no tracing overhead and no graph representation — the gradient code is directly embedded in the binary.

💡 Why this matters for ML

In Chapter 8, you wrote a 120-line backward pass by hand. With @differentiable, that entire backward pass is generated automatically — and it's often faster because the compiler can inline and optimize the gradient expressions.

Vectorized autodiff with SIMD

Mojo's autodiff works with SIMD types, which means you can differentiate vector-valued functions that operate on entire tensors at once. The compiler generates SIMD-width gradient instructions, processing 4, 8, or 16 elements in parallel per instruction.

vectorized autodiff
from math import exp

@differentiable
def vector_relu[N: Int](x: SIMD[float32, N]) -> SIMD[float32, N]:
    return max(x, 0.0)

@differentiable
def softmax[N: Int](x: SIMD[float32, N]) -> SIMD[float32, N]:
    var exp_x = exp(x)
    return exp_x / exp_x.reduce_add()

# grad computes the Jacobian for vector inputs
var inputs = SIMD[float32, 8](1.0, 2.0, 3.0, 0.0,
                        -1.0, 0.5, 4.0, -2.0)
var grad_relu = grad(vector_relu)
var grad_input = grad_relu(inputs)
# grad_input = SIMD[1,1,1,0,0,1,1,0]

Compile-time metaprogramming with comptime

Mojo's comptime keyword lets you execute code at compile time. This is different from C++'s constexpr (limited to simple expressions) or Zig's comptime (similar but less integrated with the type system). In Mojo, comptime can run arbitrary code including loops, function calls, and type manipulation.

comptime.mojo
# Mojo — comptime generates specialized code

# Compile-time loop unrolling
def dot_product[N: Int](a: SIMD[float32, N],
                          b: SIMD[float32, N]) -> Float32:
    var result: Float32 = 0.0
    comptime:
        for i in range(N):
            result += a[i] * b[i]
    return result

# Compile-time type dispatch
def to_string[T: DType](val: SIMD[T, 1]) -> String:
    comptime:
        if T == DType.float32:
            return f"Float32({val})"
        elif T == DType.int32:
            return f"Int32({val})"
        else:
            return f"Unknown({val})"

# Compile-time table generation
struct LookupTable[N: Int]:
    var values: SIMD[float64, N]

    def __init__(out self):
        comptime:
            var table = SIMD[float64, N]()
            for i in range(N):
                table[i] = Float64(i) * 0.1
            self.values = table

var lut4 = LookupTable[4]()
var lut16 = LookupTable[16]()
# lut4.values is literally [0.0, 0.1, 0.2, 0.3]
# lut16 is [0.0, 0.1, ..., 1.5] computed at compile time

Python's nearest neighbours are np.dot(a, b) and a runtime if dtype == "float32" chain that compares dtype strings. Both re-run on every call, and neither unrolls a loop or emits a specialised version of anything.

Parameterized types and compile-time loops

The [N: Int] syntax defines a parameter — a value that's fixed at compile time. When you call dot_product[4](a, b), the compiler generates a version with the loop fully unrolled for exactly 4 iterations. Call it with [16] and you get a different, specialized version.

This is how Mojo achieves zero-cost generics: there's no runtime dispatch, no vtable lookups, no boxing. Each combination of parameters produces a unique, fully-optimized function.

When to use comptime

Use comptime when you know a value at compile time but need to use it in a context that requires a runtime value (like a loop bound or array size). The compiler evaluates the comptime block and replaces it with the result — like a macro, but type-safe and hygienic.

Materialization: compile-time type transformations

Materialization in Mojo refers to the process where the compiler converts abstract type information into concrete machine code. When you write a parameterized function, the compiler generates different code for each combination of type parameters — this is called monomorphization. Mojo takes this further with alias and type declarations that are resolved at compile time.

materialization patterns
# alias creates compile-time constants
comptime BATCH_SIZE = 64
comptime N_FEATURES = 784
comptime DTYPE = DType.float32

# Parameterized struct — one compilation per DType
struct Tensor[dt: DType, rows: Int, cols: Int]:
    var data: SIMD[dt, rows * cols]

    def matmul(self, other: Tensor[dt, cols, Int(1)])
            -> Tensor[dt, rows, Int(1)]:
        var result = Tensor[dt, rows, Int(1)]()
        for i in range(rows):
            var sum: SIMD[dt, 1] = 0.0
            for j in range(cols):
                sum += self.data[i * cols + j] * other.data[j]
            result.data[i] = sum
        return result

# Compile-time if for type-specific optimization
def fast_exp[T: DType](x: SIMD[T, 1]) -> SIMD[T, 1]:
    comptime:
        if T == DType.float32:
            return Intrinsic.exp_f32(x)
        elif T == DType.float64:
            return Intrinsic.exp_f64(x)
        else:
            return generic_exp(x)

Each instantiation of Tensor with different parameters produces a completely separate type in the compiled binary. There's no runtime overhead — the compiler eliminates all branches that don't apply to the current type instantiation.
