📜 Mojo Syntax for Python Readers: def, var, and structs

A guided translation of Python's familiar shapes into Mojo's compiled equivalents — enough to read every chapter that follows without getting lost in the syntax.

Mojo looks like Python because it was designed to. Indentation-based blocks, for loops, list comprehensions, t-strings — the reading experience is intentionally familiar. But beneath the surface, Mojo is a compiled language with static typing, ownership semantics, and a compiler that turns your code into machine-native instructions.

This chapter walks through the three constructs you'll encounter most often in this book: functions (def), variables (var), and structs (Mojo's answer to Python classes). By the end, you'll be able to read any Mojo example in the chapters that follow.

def — one function keyword

Mojo 1.x has a single function keyword: def, working almost exactly like Python's def. Add explicit type annotations and you get strict, fully-checked, optimizable code — annotations are enforced at compile time and ownership rules apply.

functions.mojo
# Mojo — def with full type annotations
def add(a: Int, b: Int) -> Int:
    return a + b

# Optional arguments (default values)
def my_pow(base: Int, exp: Int = 2) -> Int:
    return base ** exp

# Variadic arguments
def sum_all(*values: Int) -> Int:
    var total: Int = 0
    for v in values:
        total += v
    return total

# Error handling with raises
def divide(a: Float64, b: Float64) raises -> Float64:
    if b == 0.0:
        raise Error("Division by zero")
    return a / b

def strict_add(a: Int, b: Int) -> Int:
    return a + b  # same result, stricter checking

Notice how similar the API surface is — Mojo borrows Python's optional args, variadic args, and raise syntax directly. Two habits change: there is no builtin sum over a variadic, so sum_all accumulates with a var loop, and a failure is raise Error(...) rather than a typed ValueError — the raises declaration above is what makes that legal.

Key differences to internalize:

  • Type annotations are enforced at compile time. Passing a String where an Int is expected is a compile error, not a runtime crash.
  • raises must be declared explicitly. Unlike Python, where any function can raise at any time, Mojo requires you to opt in.
  • self is implicit in methods. Mojo uses self as an implicit first argument in methods, just like Python, but the ownership convention on it is explicit (self, mut self, deinit self).

Variables: var only

Mojo 1.x has a single variable declaration keyword: var. The declaration is mandatory — a first assignment without var is a deprecation error in 1.0. If you don't reassign a variable, just don't reassign it. A type annotation is required when the type cannot be inferred.

variables.mojo
# Explicit type annotation
var greeting: String = "Hello World"
var count: Int = 0
var pi: Float64 = 3.14159

# Type inference — compiler figures it out
var name = "Mojo"        # inferred as String
var temperature = 22.5   # inferred as Float64

# Conventionally constant: declared once, never reassigned
var max_retries = 3      # just don't reassign it

# Late initialization
var result: Float64
if condition:
    result = compute_a()
else:
    result = compute_b()

# Copying and moving
var first = [1, 2, 3]
var second = first.copy()   # explicit copy
var third = first^          # move (transfers ownership)

The Python version of this file needs no annotations at all, has no block scope — a name first assigned inside an if is still live afterwards, which is why the result declaration above sits outside both branches — and binding a second name to a list makes an alias, not a copy. Mojo spells those last two operations first.copy() and first^.

The critical difference from Python: Mojo variables are statically typed. Once you assign a value to a variable, its type is locked in. You cannot reassign a String variable to an Int. This is what enables the compiler to generate fast, predictable code.

The ownership twist

When you write var b = a^, you move the value from a into b. After the move, a is uninitialized and cannot be used. This is Mojo's memory safety model — no garbage collector, no hidden copies, no double-free bugs.

Structs: Mojo's primary data type

If you're coming from Python, think of structs as classes that are checked at compile time. They have fields, methods, constructors, and destructors — but no inheritance (use traits for that), no dynamic dispatch, and no runtime type information. Structs are what make Mojo fast: the compiler knows exactly how much memory each struct needs and can optimize accordingly.

structs.mojo
# Mojo — struct with fieldwise init
from std.math import sqrt

@fieldwise_init
struct Point:
    var x: Float64
    var y: Float64

    def distance_to(self, other: Point) -> Float64:
        return sqrt((self.x - other.x)**2 + (self.y - other.y)**2)

# Usage
var p1 = Point(x=3.0, y=4.0)
var p2 = Point(x=0.0, y=0.0)
var d = p1.distance_to(p2)
print(d)  # 5.0

The @fieldwise_init decorator generates a constructor that initializes each field from its argument — equivalent to Python's @dataclass. Without it, you'd write the constructor manually using def __init__(out self, ...). One Python habit does not carry over: a method taking another Point has to quote the type as -> "Point", because the class body is not finished when the signature is read. Mojo names the type directly.

Methods and mutation

Methods in Mojo use self as the first argument (just like Python). To modify fields, mark the method with mut:

mutation in Mojo structs
@fieldwise_init
struct Counter:
    var value: Int

    def increment(mut self):
        self.value += 1

    def get(self) -> Int:
        return self.value

var c = Counter(value=0)
c.increment()
print(c.get())  # 1
💡 Key insight

Mojo structs are not copyable by default. If you want to copy a struct, it must implement the Copyable trait. This is intentional — it prevents accidental expensive copies and forces you to think about ownership.

Traits: Mojo's version of interfaces

Since Mojo structs can't inherit from each other (no class hierarchies), traits serve as the mechanism for defining shared behavior. A trait is a contract: any struct that implements a trait must provide the methods the trait requires.

defining and using traits
# Define a trait
trait Describable:
    def describe(self) -> String: ...

# Implement the trait
@fieldwise_init
struct Dog(Describable):
    var name: String
    var breed: String

    def describe(self) -> String:
        return f"{self.name} the {self.breed}"

# Generic function — works with ANY type that implements Describable
def print_description[T: Describable](item: T):
    print(item.describe())

var dog = Dog(name="Rex", breed="Labrador")
print_description(dog)  # Rex the Labrador

Traits are how Mojo achieves polymorphism without inheritance. The [T: Describable] syntax is a parameterized type — the compiler generates specialized code for each concrete type that implements the trait, giving you zero-cost abstraction.
