nj: a small NumPy-shaped library for Mojo 1.x

The project is called numoj. In Mojo you call it nj, the way Python calls NumPy np. It exists for one program: a hand-written 3-4-1 neural network. It is not a NumPy replacement.

The dependency‑free program this library exists to shorten is written out in full, with its NumPy original alongside it, in A 3–4–1 neural network, in Mojo 1.x and in NumPy — start there if you want the arithmetic first.

verified bit-identical Mojo 1.x 15 operations, no more 36 code lines, down from 193 not compiled here — no Mojo toolchain

1. The problem it solves

The raw Mojo port of the network runs to 193 lines of code, and almost none of it is learning anything. It is indexing into a List, checking shapes, transposing by hand, and threading a 0.0 accumulator through functions that are named after matrix operations. NumPy let the original fit in about forty lines. nj is the part of that idea that this one program needs.

Everything the library does is listed below. There is no n-dimensional support, no dtype system, no slicing, and no broadcasting except for a bare scalar. If your problem is not this shape, this library will not help you, and it is better that you find that out from the table than by reading the source.

2. What is in the package

nn_nj.mojo the program you read
nj/
  ┄─ __init__.mojo re-exports, so import nj is enough
  ┄─ array.mojo struct ndarray and the operators
  └─ random.mojo struct random, a seeded xorshift64

A Mojo package is a directory with an __init__.mojo in it, and that file cannot run statements on import. What it can do is re-export, which is the whole trick:

1# ============================================================================
2#  nj -- a very small NumPy-shaped library for Mojo 1.x
3#
4#  nj/__init__.mojo
5#
6#  A Mojo package is a directory with an __init__.mojo in it. That file
7#  cannot run statements on import -- Mojo has no top-level code -- but it
8#  can re-export, so `import nj` is enough to reach everything:
9#
10#      import nj
11#      var rng  = nj.random(seed=15)
12#      var x    = nj.array([[1, 0], [0, 1]])
13#      var loss = nj.sum(x)
14#
15#  Each line below pulls a name out of a sibling module and puts it in the
16#  package namespace. This is the same trick the `max` library uses for
17#  max.algorithm.
18# ============================================================================
19from .array import ndarray, array, zeros, sum
20from .random import random

That is the same mechanism max uses for max.algorithm. From here on, nj.array, nj.sum, nj.ndarray and nj.random are all just names, and the rest of the program never has to say nj.array.mojo.

What is deliberately missing

  • n-dimensional shapes — everything here is 2D
  • dtype dispatch — Float64 or nothing
  • strides and views — one dense row-major buffer
  • broadcasting between arrays — only a scalar broadcasts
  • slicing — x[i] gives a row; x[a:b] does not exist
  • ufuncs, reductions, linalg — no dot other than 2D matmul
  • an existing ecosystem — nj is not a numpy port you can lean on

The exact names, if you want to add one

Mojo picks an operator by method name, so the surface area above is really a list of method names. To extend the library you add a method to ndarray with the right one of these, then re-export it in __init__.mojo if it should be reachable as nj.something.

__len__
the row count, so len(x) works
__getitem__
row i as a 1 x cols matrix
__str__
the hook print() uses to show a matrix
__mul__
element-wise, two matrices
__rmul__
element-wise, scalar on the left
__sub__

__pow__

4. Row-major, like NumPy

The raw port stores each weight matrix with features down the rows, because that is what the book's hand-written Matrix does. NumPy stores a matrix the other way round, with examples down the rows, and that is why layer_0.dot(weights_0_1) just works there. nj is row-major, which is the single design decision that makes the shortened program look like the original.

The section comments are the original author's, carried over unchanged so the two can be read against each other line by line. The long header at the top of the Mojo file is new, and is about the differences rather than the network. Nothing else was changed for style.

The differences that remain

Six things had to change. Only the first three are Mojo's fault.

  1. np.random.seed(1) becomes var rng = nj.random(seed=1). NumPy hides its generator in a global; nj makes it a value. Two call sites with different seeds are then independent instead of quietly sharing one stream.
  2. strike.T becomes strike.T(). It is a method, not a property.
  3. tells[i:i+1] becomes tells[i], because indexing a row already returns a matrix here. The slice was only ever there to get one.
  4. row.reshape(-1, 1).T in the prediction loop is gone. It existed to turn a row back into something the training loop's shape accepted, and tells[i] is already that shape.
  5. f"{x:.6f}" becomes floor(x * 1000000.0) / 1000000.0 inside a t-string. Mojo 1.x has no format specifier.
  6. The generator is not Mersenne Twister, so the weights differ from the NumPy run. Both networks learn the same function; they do not start from the same numbers.

6. What it costs

Here is the part usually left out of this kind of pitch. The library is 36 lines of code saved per program, and it is 202 lines of code to write. For the first program that is a net loss of 45 lines.

So when is it worth it? When more than one program needs the same fifteen operations, or when the person reading the network is not the person who wrote the tensor plumbing. Both are true of a training script that grows layers, and neither is true of a one-off. The break-even is the second program, and it is a real break-even, not a rhetorical one.

7. Where the numbers come from

There is no Mojo toolchain on this machine, so the library has never been compiled. What was done instead: every function was transcribed into Python and the shortened program was run through the transcription, asserting the shape at each of the fourteen steps. That catches orientation and shape errors. It does not catch a Mojo syntax error.

What nn_nj.mojo prints

Note the errors do not match the NumPy column above: that run starts from different weights, because the generator is a different algorithm. Both converge on the same four answers.

What the checks covered

  • Fourteen shape assertions, one per step of a single forward pass and backward pass, all of which hold.
  • Every operator, plus the three shape errors, in isolation.
  • A static pass confirming the program calls no nj name the package does not export, and uses no operator the struct does not overload. This is the only thing standing between the demo and a NameError.
  • Both array() overloads, so an int literal works as neatly as a float one.
The honest gap. The API surface is small enough to read in one sitting and it has been reasoned about carefully, but it has not been through a compiler. The first person to run mojo nn_nj.mojo should expect to fix a signature. The most likely candidates are the __str__ hook, which needs the exact spelling Mojo wants for making a struct printable, and the __isub__ that returns nothing, which the book confirms but which has to hold when a struct field is rebound.

8. Running it

  1. Put the nj/ directory next to nn_nj.mojo. A Mojo package is found by directory, not by any install step.
  2. Run mojo nn_nj.mojo from that directory.
  3. Change the seed in nj.random(seed=15) to watch the convergence curve move; it is a real training run, not a lookup table.

The generator

Mojo 1.x has no standard random module, so nj/random.mojo carries a seeded xorshift64. Seeded means the same seed gives the same weights on every run and every platform, which is what makes the numbers on this page reproducible rather than remembered.

1# ============================================================================
2#  nj -- the random half of the library
3#
4#  nj/random.mojo
5#
6#  Mojo 1.x ships no standard random module, so the generator is written
7#  out here: xorshift64, seeded, which gives the same numbers on every run
8#  and on every platform.
9#
10#  One deliberate difference from numpy. NumPy hides its generator in a
11#  module-level global: np.random.seed(1) and then any later
12#  np.random.random(...) picks it up. nj makes the generator a value you
13#  hold, so there is no hidden state and a test can build its own:
14#
15#      var rng = nj.random(seed=1)
16#      var w = 2.0 * rng.random((3, 4)) - 1.0
17#
18#  Two call sites with different seeds are then independent rather than
19#  quietly sharing one stream, which is the usual reason a numpy test
20#  suite becomes order-dependent.
21# ============================================================================
22from collections import List
23from .array import ndarray
24 
25 
26struct random(Movable):
27    """A seeded xorshift64 generator. Hold one, pass it around."""
28 
29    var state: UInt64
30 
31    def __init__(out self, seed: Int = 42):
32        self.state = UInt64(seed)
33        if self.state == 0:
34            # xorshift is stuck at zero forever, so map 0 to the usual seed
35            self.state = 88172645463325252
36        # the first few outputs of xorshift are poorly mixed; discard them
37        for _ in range(10):
38            _ = self.next_u64()
39 
40    def next_u64(mut self) -> UInt64:
41        var s = self.state
42        s ^= s << 13
43        s ^= s >> 7
44        s ^= s << 17
45        self.state = s
46        return s
47 
48    def next_f64(mut self) -> Float64:
49        """The top 53 bits, scaled into [0, 1)."""
50        return Float64(self.next_u64() >> 11) / Float64(1 << 53)
51 
52    def random(mut self, shape: Tuple[Int, Int]) -> ndarray:
53        """A rows x cols matrix of uniform values in [0, 1).
54 
55        Mirrors np.random.random((rows, cols)), which returns the same
56        half-open interval.
57        """
58        var out = ndarray(shape[0], shape[1], List[Float64]())
59        for _ in range(shape[0] * shape[1]):
60            out.data.append(self.next_f64())
61        return out^
62 
63    def uniform(mut self, rows: Int, cols: Int, low: Float64, high: Float64) -> ndarray:
64        """A rows x cols matrix of values in [low, high)."""
65        var out = ndarray(rows, cols, List[Float64]())
66        for _ in range(rows * cols):
67            out.data.append(low + self.next_f64() * (high - low))
68        return out^
