📦 Packaging, Testing, and Shipping Mojo Projects

From source files to a reliable artifact — how Mojo's project model, built-in test runner, and benchmarking tools get your data pipeline from a notebook to production.

Mojo project structure

A Mojo project follows a straightforward convention that will feel familiar to Python developers. The root of your project contains a mojoproject.toml manifest that declares metadata, dependencies, and build targets — the Mojo equivalent of pyproject.toml.

typical Mojo project layout
my_project/
├── mojoproject.toml
├── src/
│   ├── __init__.mojo
│   ├── data_loader.mojo
│   └── pipeline.mojo
├── tests/
│   ├── test_data_loader.mojo
│   └── test_pipeline.mojo
├── examples/
│   └── demo.mojo
└── README.md

The mojoproject.toml file declares your project identity and its dependencies:

mojoproject.toml
# Mojo project manifest
[project]
name = "ml_pipeline"
version = "0.3.1"
description = "Production ML data pipeline"
authors = [{name = "Your Name", email = "you@example.com"}]

[dependencies]
max-engine = "^1.0"
numpy = "^1.26"

[features]
avx512 = ["max-engine/avx512"]

[bin]
name = "pipeline"
source = "src/main.mojo"

The pyproject.toml equivalent is the same [project] table with three different keys: requires-python = ">=3.11" instead of a MAX version, a [project.dependencies] table instead of [dependencies], and a [project.scripts] entry pointing at src.main:main — so Python has to name both the module and the function to produce one runnable command.

Unlike Python, where source files are scattered into packages with __init__.py, Mojo projects use a clean src/ layout. The compiler resolves imports from the src/ directory automatically, so you never need to manipulate sys.path or install your own package in editable mode.

💡 Why this matters

In Python, most production bugs trace back to "it works on my machine" — a dependency is missing, a version is wrong, or the wrong Python is active. Mojo's mojoproject.toml pins exact versions and resolves the entire dependency graph at build time, eliminating this class of errors entirely.

Package management and dependency resolution

Mojo's package manager is built into the compiler. When you run mojo build, it reads mojoproject.toml, resolves all dependencies, downloads what's needed, and compiles everything into a single binary. There's no equivalent of pip install — the entire dependency lifecycle is managed by the build system.

managing dependencies
# Add a dependency to your project
mojo add max-engine

# Add a specific version
mojo add numpy@1.26.4

# Remove a dependency
mojo remove numpy

# List all resolved dependencies
mojo list

# Build the project (resolves + compiles)
mojo build

# Build with optimization
mojo build -O3

# Run the project
mojo run src/main.mojo

For data science teams, this means reproducibility is built in. When a teammate checks out your repository and runs mojo build, they get the exact same binary, built with the exact same dependencies, on their machine. No virtual environments, no conda conflicts, no "install these 12 packages in this exact order."

importing packages.mojo
from max.engine import InferenceSession
from math import sqrt, sin, cos
from collections import Dict

def load_model(path: String) -> InferenceSession:
    var session = InferenceSession(path)
    return session

The same three imports in Python read from max.engine import InferenceSession, from math import sqrt, sin, cos, and from collections import defaultdict — with str where this page says String, and defaultdict where this page says Dict. Same lookup, different vocabulary.

Testing with MojoTest

Mojo ships with a built-in test framework that integrates directly with the compiler. You don't need to install pytest or unittest — the test runner is part of the mojo command. Tests are just Mojo files with functions decorated with @test.

test_data_loader.mojo
from testing import test, assert_equal, assert_true

# Simple assertion test
@test
def test_csv_parsing():
    var rows = parse_csv("name,age\nAlice,30\nBob,25")
    assert_equal(rows.num_rows(), 2)
    assert_equal(rows[0]["name"], "Alice")
    assert_equal(rows[0]["age"], "30")

# Test with exception expectation
@test
def test_empty_input_raises():
    try:
        parse_csv("")
        assert_true(False, "Should have raised ValueError")
    except Error:
        pass  # expected

# Parameterized test
@test
def test_normalize_values():
    var cases = [(0.0, 0.0), (5.0, 1.0), (-3.0, 0.0)]
    for input_val, expected in cases:
        assert_equal(normalize(input_val), expected)

The pytest spelling of those same three tests needs import pytest, wraps the raising case in with pytest.raises(ValueError):, and replaces the hand-written case list with @pytest.mark.parametrize("input_val,expected", [...]) — a decorator that generates one test function per row, and that pytest has to reflect over at collection time.

Running your tests is a single command:

running tests
# Run all tests in the project
mojo test

# Run tests in a specific file
mojo test tests/test_data_loader.mojo

# Run with verbose output
mojo test -v

# Run tests matching a pattern
mojo test --filter csv

MojoTest has a significant advantage over Python testing in data science: because tests run compiled code, they execute orders of magnitude faster. A test suite that takes 45 seconds in pytest can complete in under a second with MojoTest, which fundamentally changes how you approach testing in a data pipeline.

Testing strategy for data pipelines

Use pure Mojo tests for transformation logic, schema validation, and output format checks. Use integration tests that call into Python (via Python.import_module) for testing model predictions against known-good outputs. Reserve notebook-level testing for exploratory validation only.

Benchmarking your Mojo code

Performance is the reason you chose Mojo over Python. But how do you know if your Mojo code is actually faster? The benchmark module provides a rigorous way to measure execution time, memory allocation, and throughput — with statistical rigor that avoids common benchmarking pitfalls like measuring warmup time or GC pauses.

bench_transform.mojo
from benchmark import keep_running, benchmark_function
from random import randn

def standardize(data: List[Float64]) -> List[Float64]:
    var n = len(data)
    var mean: Float64 = 0.0
    for v in data:
        mean += v
    mean /= n

    var std: Float64 = 0.0
    for v in data:
        std += (v - mean) ** 2
    std = (std / n) ** 0.5

    var result = List[Float64](capacity=n)
    for v in data:
        result.append((v - mean) / std)
    return result

def main():
    var data = randn[Float64](1_000_000)

    def bench():
        _ = standardize(data)

    var stats = benchmark_function(bench, iterations=50, warmup=10)
    print(f"Median: {stats.median:.4f}s")
    print(f"Mean:   {stats.mean:.4f}s")
    print(f"Stddev: {stats.stddev:.4f}s")

The numpy version of standardize is np.mean and np.std in three lines, timed with timeit.timeit(lambda: standardize(data), number=50) — one wall-clock number, carrying every failure mode the next paragraph names: no warmup, no distribution, and GC time counted as work.

The Mojo benchmarking module is integrated with the compiler — it knows about SIMD width, cache line alignment, and allocation patterns. It can detect when your benchmark is measuring garbage collection instead of actual work, something Python's timeit cannot do automatically.

CI/CD and deployment

Mojo projects deploy as compiled binaries. This is fundamentally different from Python, where you ship source code and a requirements file and hope the deployment environment has the right interpreter. A Mojo binary includes everything — no runtime dependencies, no interpreter, no shared libraries to hunt down.

.github/workflows/ci.yml
# Mojo CI — builds a binary artifact
name: Mojo CI
on: [push, pull_request]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Mojo
        uses: modular/setup-mojo@v2
        with:
          version: latest

      - name: Resolve dependencies
        run: mojo install

      - name: Run tests
        run: mojo test

      - name: Build binary
        run: mojo build -O3 --release

      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: pipeline-binary
          path: build/

The Python workflow for the same repository needs an actions/setup-python@v5 step, a pip install -r requirements.txt step, and a build step that produces a wheel rather than an executable — python -m build — so the pipeline-binary artifact above has no direct counterpart to upload.

🛠️ Practical tip

For most data science teams, the simplest deployment path is: compile a Mojo binary, wrap it in a Docker container with your data volume mounted, and schedule it with Airflow or Kubernetes. You get Python-level development speed with C-level runtime performance.
